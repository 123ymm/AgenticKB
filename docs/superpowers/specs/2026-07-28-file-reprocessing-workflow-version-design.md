# 文件重复挖掘与 Workflow 版本切换方案

## 1. 文档状态

- 状态：当前方案草案
- 日期：2026-07-28
- 范围：产品方案与业务规则，不包含代码、接口和数据库实现设计

## 2. 背景

用户可能先使用某个挖掘 Workflow 处理一批文件，之后又希望使用另一种 Workflow 重新处理其中的部分文件。系统同时还需要处理重复上传、文件下架后恢复、历史加工结果复用以及不同 Workflow 结果切换等情况。

如果仅按“文件是否存在”决定跳过或重挖，会产生以下问题：

- 同一文件使用不同 Workflow 时无法区分加工结果；
- 同一个 Workflow 的不同发布版本可能被误判为相同；
- 文件下架后，历史产物可能可恢复，也可能已经被清理；
- 重新挖掘失败时可能错误覆盖当前可用知识资产；
- 批量上传时逐文件弹窗确认，用户体验较差；
- 文件虽然复用了旧结果，仍然需要保留本次上传批次的审计关系。

本方案通过“上传预检 + 单一当前版本 + 可恢复历史版本”解决上述问题。

## 3. 已确认原则

### 3.1 单一当前加工版本

同一 Domain 下的同一文件，在同一时间只能有一个当前有效加工版本。

同一文件使用其他 Workflow 或其他 Workflow 版本生成的结果，可以作为历史加工版本保留。历史加工版本不参与当前检索和知识服务，但在产物仍完整时可以恢复。

补充约束：一个 Snapshot 只能冻结绑定一个精确 Workflow 发布版本（`workflow_id + workflow_version + workflow_graph_hash`）。同一文件重新使用其他 Workflow 加工时必须生成候选 Snapshot，不能在候选执行期间改写当前有效 Snapshot；新 Snapshot 发布成功后才替换当前有效选择。未生效的候选或历史 Workflow Snapshot 不参与检索，可由后续生命周期清理或覆盖其非当前产物。

### 3.2 先预检，再创建正式挖掘任务

用户上传一批文件并选择 Workflow 后，系统先完成文件哈希计算和历史版本匹配，生成本批次的预检结果。用户确认处理计划后，系统才创建正式挖掘任务。

### 3.3 冲突项默认保留当前版本

当相同文件已经存在当前有效版本，但本次选择了不同的挖掘方式时，该文件属于 Workflow 冲突项。

冲突项默认勾选“保留当前版本”，防止用户在批量确认时误覆盖已有知识资产。用户可以显式改为“使用新 Workflow 重新挖掘”或“切换到可恢复历史版本”。

### 3.4 成功后切换，失败不影响当前版本

重新挖掘期间，原有当前版本继续对外生效。新版本只有在执行成功并完成知识资产发布后，才成为当前有效版本。

如果重新挖掘失败，原有当前版本保持不变。

## 4. 核心概念

### 4.1 逻辑文件

逻辑文件表示当前 Domain 中的一份文件内容。第一阶段使用以下信息识别：

```text
Domain + 文件原始内容哈希
```

文件名、上传批次、来源路径等属于“来源记录”，不直接作为文件内容是否相同的判断条件。同一内容可以被多个批次或多个来源记录引用。

### 4.2 加工版本

加工版本表示某个逻辑文件经过一次确定的挖掘方式处理后形成的一组完整派生资产，包括但不限于：

- 解析与切分结果；
- 语义增强结果；
- 检索单元和向量；
- 实体、关系和本体候选；
- 对应的 build/release 关系；
- 完整的执行与来源审计信息。

一个逻辑文件可以拥有多个加工版本，但只能有一个当前有效加工版本。

### 4.3 挖掘指纹

不能只使用 `workflow_id` 判断两次挖掘是否完全相同，因为同一 Workflow 可以发布多个不可变版本。

当前方案使用“挖掘指纹”判断加工结果是否可以安全复用。基础范围为：

```text
Domain
+ 文件原始内容哈希
+ workflow_id
+ workflow_version
+ workflow_graph_hash
+ 本体版本
```

如果模型、Prompt、Embedding 模型或其他运行配置会实质改变产物，后续应将其冻结到执行上下文，并纳入挖掘指纹。

### 4.4 加工版本状态

加工版本至少需要在产品语义上区分：

- 当前有效：正在参与当前知识服务；
- 历史可恢复：不再生效，但完整产物仍然保留；
- 历史不可恢复：保留审计记录，但产物已经清理；
- 候选版本：正在挖掘或已经挖掘完成但尚未发布；
- 失败版本：本次加工失败，不允许成为当前版本。

## 5. 用户入口

### 5.1 上传新批次

```text
上传文件
→ 选择已发布的 Workflow 版本
→ 计算文件哈希
→ 执行预检
→ 用户确认处理计划
→ 创建正式挖掘任务
→ 执行
→ 发布并切换当前加工版本
```

### 5.2 对已有文件重新挖掘

用户不应为了更换 Workflow 而重新上传文件。知识资产页或批次详情页应提供：

```text
选择一个或多个已有文件
→ 点击“重新挖掘”
→ 选择 Workflow 版本
→ 执行同一套预检
→ 用户确认处理计划
→ 执行并发布
```

两个入口共享相同的预检规则、版本切换规则和审计语义。

## 6. 预检判定顺序

预检不能只检查当前版本，需要同时查询当前版本、历史版本和进行中的任务。

建议按照以下优先级判断：

1. 查找挖掘指纹完全相同的当前有效版本；
2. 查找挖掘指纹完全相同的进行中任务；
3. 查找挖掘指纹完全相同且产物完整的历史版本；
4. 检查该逻辑文件是否存在其他当前有效版本；
5. 检查是否只有不可恢复的历史记录；
6. 如果均不存在，则按新文件处理。

## 7. 预检分类与默认动作

| 分类 | 判定条件 | 默认动作 | 是否需要用户确认 |
|---|---|---|---|
| 新文件 | 当前 Domain 中没有相同文件哈希 | 正常挖掘 | 否 |
| 可直接复用 | 存在相同挖掘指纹的当前有效版本 | 复用当前版本 | 否 |
| 正在处理中 | 相同挖掘指纹已有任务运行 | 关联或等待已有任务 | 否 |
| 可直接恢复 | 没有其他当前版本，且存在相同挖掘指纹的可恢复历史版本 | 恢复历史版本 | 否 |
| 可切换历史版本 | 当前存在其他版本，同时存在本次挖掘指纹对应的可恢复历史版本 | 保留当前版本 | 是 |
| Workflow 冲突 | 当前存在其他版本，但没有匹配的可恢复历史版本 | 保留当前版本 | 是 |
| 无法恢复 | 只有匹配的历史记录，但产物已经清理 | 重新挖掘 | 否 |

### 7.1 可切换历史版本

例如文件当前使用 Workflow B，但历史上存在本次所选 Workflow A 的完整结果。系统不应直接重新计算，而应提供：

- 保留当前 Workflow B；
- 切换回历史 Workflow A；
- 如果用户明确需要重新生成，也可以重新挖掘 Workflow A。

默认选择“保留当前版本”。

### 7.2 Workflow 冲突

例如文件当前使用 Workflow A，但本次选择 Workflow B，且不存在可恢复的 Workflow B 历史版本。系统提供：

- 保留当前版本；
- 使用 Workflow B 重新挖掘。

默认选择“保留当前版本”。

## 8. 预检页面设计

### 8.1 汇总区域

页面顶部展示各类文件数量，例如：

```text
新挖掘 15
复用 20
恢复 3
等待已有任务 2
需要确认 5
```

### 8.2 文件明细

每个文件至少展示：

- 文件名和内容哈希摘要；
- 当前加工版本状态；
- 当前 Workflow 名称及版本；
- 本次选择的 Workflow 名称及版本；
- 是否存在可恢复的匹配历史版本；
- 系统建议动作；
- 用户最终选择的动作。

### 8.3 批量操作

需要确认的文件支持：

- 全部保留当前版本；
- 全部使用新 Workflow 重新挖掘；
- 对存在匹配历史版本的文件全部切换到历史版本；
- 逐文件配置。

系统不采用逐文件弹窗方式。冲突组首次进入页面时，所有文件默认选择“保留当前版本”。

### 8.4 文案要求

对于没有重新计算的文件，页面应使用“复用”而不是简单的“跳过”。推荐文案：

> 已存在相同加工版本，本次将直接复用，不会重复计算。

对于恢复操作，推荐文案：

> 已找到完整的历史加工版本，本次将恢复该版本，不会重新执行挖掘算子。

## 9. 处理计划

用户确认预检结果后，系统生成一份固定的本批次处理计划。每个文件都必须有明确动作，不能因为复用或保留当前版本而从批次中消失。

建议的业务动作包括：

| 动作 | 含义 |
|---|---|
| `NEW` | 新文件，执行挖掘 |
| `REUSED` | 复用相同的当前加工版本 |
| `RESTORED` | 恢复相同的历史加工版本 |
| `REMINED` | 使用所选 Workflow 重新挖掘 |
| `KEPT_CURRENT` | 保留当前版本，本批次不改变知识资产 |
| `JOINED_EXISTING` | 关联或等待已经运行的相同任务 |

处理计划需要记录预检时的文件状态和用户最终决策，以便后续审计。

如果用户确认前文件状态已经被其他任务改变，应刷新受影响文件的预检结果，而不是继续执行过期计划。

## 10. 执行与版本切换

### 10.1 重新挖掘

重新挖掘产生候选加工版本。候选版本在完成发布前不能替换当前版本，也不能参与线上检索。

### 10.2 发布成功

发布成功后，对每个需要切换的文件执行以下语义：

1. 新加工版本成为当前有效版本；
2. 原当前版本转为历史可恢复版本；
3. 当前知识资产完整切换到新版本；
4. 新 Workflow 未产生的旧派生资产必须退出当前版本，不能残留；
5. 版本切换和知识资产发布应保持一致，不能出现一半新、一半旧的状态。

### 10.3 执行失败

如果新加工版本执行失败：

- 原当前版本继续有效；
- 失败结果不得进入当前知识资产；
- 保留失败记录和错误信息；
- 用户可以从失败任务重新发起挖掘。

## 11. 恢复语义

“已下架”不等于“一定可以直接恢复”。执行恢复前需要确认：

- 原始文件或可用来源仍然存在；
- 加工快照完整；
- 检索单元、向量、实体和关系等必要产物仍然存在；
- 对应 Workflow Manifest 和版本信息仍可追溯；
- 恢复后能够重新完成 build/release。

满足条件的版本标记为“历史可恢复”。产物已经被物理清理的版本只能保留审计记录，必须重新挖掘。

如果恢复历史版本时存在另一个当前有效版本，恢复属于一次版本切换，默认仍然保留当前版本，只有用户显式选择后才执行恢复。

## 12. 批次与来源审计

上传批次表示一次用户提交行为，逻辑文件表示文件内容，加工版本表示挖掘结果，三者不能混为一体。

即使文件被复用、恢复或保留当前版本，本次批次仍要记录该文件及其动作。批次详情需要能够回答：

- 用户本次提交了哪些文件；
- 哪些文件实际执行了挖掘；
- 哪些文件复用了已有结果；
- 哪些文件恢复了历史版本；
- 哪些冲突文件选择了保留当前版本；
- 每个文件最终关联了哪个加工版本。

同一逻辑文件可以被多个上传批次引用。删除或下架某个批次时，不能在仍有其他有效来源引用的情况下错误删除共享文件。

## 13. 并发与重复提交

两个用户或两个批次可能同时提交相同文件。产品规则为：

- 相同文件和相同挖掘指纹已经运行时，不重复启动任务；
- 新提交关联或等待现有任务；
- 相同文件使用不同挖掘指纹时，可以生成独立候选版本；
- 同一文件的当前版本切换必须串行化；
- 后发布的任务不能静默覆盖用户基于旧预检结果作出的决定。

## 14. 下架与历史保留

下架当前文件时：

- 当前加工版本退出当前知识资产；
- 如果产物仍保留，则转为历史可恢复状态；
- 其他历史加工版本保持历史状态；
- 后续选择相同挖掘指纹时可以直接恢复；
- 后续选择不同挖掘指纹时重新挖掘。

物理清理历史产物属于单独的生命周期操作，不能与普通下架混同。

## 15. 验收标准

方案落地后应满足：

1. 相同文件和相同挖掘指纹不会重复计算；
2. 相同文件使用不同 Workflow 时不会被静默覆盖；
3. 冲突项默认保留当前版本；
4. 用户可以批量修改冲突项处理方式；
5. 可恢复历史版本可以不经重算重新生效；
6. 不可恢复历史版本不会被错误恢复；
7. 重挖失败不会影响当前有效版本；
8. 发布成功后同一文件只有一个当前有效加工版本；
9. 新版本不会遗留旧版本独有的派生资产；
10. 复用、恢复、重挖和保留动作都能在批次和文件历史中追溯；
11. 用户可以从已有文件直接发起重新挖掘，无需重新上传；
12. 并发提交不会产生重复任务或静默覆盖。

## 16. 待后续确认

以下内容尚未最终拍板，需要在进入实现方案前继续确认：

1. 部分文件挖掘失败时，是允许成功文件部分发布，还是整批保持原状；
2. 挖掘指纹除 Workflow、本体版本外，是否必须包含 LLM、Prompt 和 Embedding 模型版本；
3. 原始字节哈希相同但文件名或来源元数据不同，是否始终视为同一逻辑文件；
4. 历史加工版本的默认保留期限，以及何时转为不可恢复；
5. `JOINED_EXISTING` 是等待现有任务完成，还是仅记录关联并立即返回；
6. 用户选择切换历史版本时，是否需要再次展示影响范围确认；
7. 预检结果允许保留多久，以及确认时的状态变化处理策略。

## 附录 A：Workflow 编辑器信息架构补充

本节记录 2026-07-28 已确认的 Workflow 编辑器设计。算子在目录中的分组用于表达业务能力归属，`zone` 用于表达运行范围，二者不再混用。

### A.1 左侧算子目录分组

左侧目录按业务能力分为以下五组：

| 业务分组 | 算子 |
|---|---|
| 输入与解析 | 输入发现 `input_ingest`、解析与切分 `parse_segment` |
| 篇章与检索 | 语义增强 `enrich`、篇章关系抽取 `discourse_line`、上下文检索增强 `contextual_retrieval_enrich`、检索单元生成 `retrieval_unit_build`、向量化 `embedding` |
| 实体与图谱 | 实体抽取 `entity_extract`、实体归一 `entity_resolve`、实体关系抽取 `entity_relation_extract`、实体审核 `entity_review_gate`、图谱写入 `graph_write` |
| 本体演化 | 本体归纳 `ontology_induction`、本体审核 `ontology_review_gate` |
| 资产与发布 | 资产持久化 `asset_persist`、挖掘收尾 `mining_finalize` |

每个算子卡片额外展示运行范围标签：

- `input`：输入阶段；
- `document`：逐文档执行；
- `global`：整批次聚合执行。

业务分组决定目录位置，运行范围标签解释执行语义，颜色继续表达算子类别和职责。左侧目录与右侧画布中的同一算子必须使用一致的主色，帮助用户快速建立视觉对应关系。

### A.2 画布执行位置

实体审核、本体归纳、本体审核、图谱写入四个算子保留在资产持久化之后，形成以下执行顺序：

```text
文档能力线汇合
→ 资产持久化
→ 实体审核
→ 本体归纳（可选）
→ 本体审核（启用本体归纳时必需）
→ 图谱写入
→ 挖掘收尾 / Build / Publish
```

这里的“资产持久化”和“图谱写入”是两个不同层级的持久化动作：

- 资产持久化负责逐文档产物，包括解析、篇章、检索以及实体候选等文档级资产；
- 图谱写入负责审核通过后的 Domain 级规范实体、关系和本体结果；
- 图谱写入必须位于审核之后，不能合并进审核之前的资产持久化；
- 四个算子虽然运行范围是 `global`，但在业务语义上仍属于实体图谱和本体演化能力线，不应因为 `global` 被展示成独立的业务分类。

### A.3 动态编辑状态

目录卡片、画布节点、右侧检查器、删除按钮、快捷键和发布校验必须使用同一套“当前有效编辑策略”，不能只展示 Catalog 中静态的 `editPolicy`。

界面统一使用以下三个用户可理解的状态：

- 固定骨架：始终不可删除，例如输入发现、解析与切分、资产持久化、挖掘收尾；
- 当前必需：因为当前画布包含相关能力线而暂时不可删除；
- 可选：当前允许添加、编辑或删除。

当前必需状态按画布内容动态计算：

| 当前画布内容 | 当前必需算子 |
|---|---|
| 不包含实体能力线，也不包含本体归纳 | 无条件保护算子 |
| 包含实体抽取、实体归一、实体关系抽取中的任意一个 | 实体审核、图谱写入 |
| 包含本体归纳 | 实体审核、本体审核、图谱写入 |

本体归纳本身保持可选；当用户删除本体归纳后，本体审核应立即从“当前必需”变为“可选”。状态变化应即时反映在目录、节点标记和操作按钮上，并提供原因提示，例如“当前存在实体能力线，发布前必须完成实体审核”。

### A.4 验收标准

1. 左侧目录按五个业务分组展示全部 16 个算子；
2. 同一算子在目录和画布中的颜色一致；
3. 运行范围作为辅助标签展示，不再直接充当业务分组；
4. 实体审核、本体归纳、本体审核、图谱写入位于资产持久化之后、挖掘收尾之前；
5. 用户能够理解资产持久化与图谱写入分别处理文档级资产和 Domain 级规范图谱；
6. 受保护状态随当前画布能力线即时变化；
7. 所有展示和操作入口使用同一套当前有效编辑策略。
