# AgenticKB 数据库收敛最终决策

> 状态：最终决策版本，作为下一版本实现真相源  
> 日期：2026-09-17  
> 范围：Mining/LLM 指定启动链 67 张表 + Java 独立启动链 3 张表

## CAPABILITY

下一版本把数据库从“功能预留、旧链兼容和研究代码不断加表”收敛为只承载当前产品能力
的模型。新建库直接采用干净基线；已运行数据库先上线不再依赖退役表的兼容代码，再由
显式、可预检、幂等的一次性迁移删除历史表。保留表必须有真实读写、明确生命周期，或
承担必要的完整性/原子晋升职责。

## 核心数据不变量

### 1. 文档三层模型保留

```text
asset_documents
→ asset_document_snapshot_links
→ asset_document_snapshots
```

- document 是身份；
- snapshot 是可共享知识成果；
- link 是文档、源版本与 snapshot 的关系。

### 2. Build 是全量视图

Run 可以增量执行，但每个 validated Build 必须是完整可检索视图，不是差异包。

```text
新 Build 可用知识
= 上一个有效 Build 可用知识
- 明确删除的文档
+ 本次首次成功文档
+ 本次更新成功的新快照
```

- SKIP 文档继续选择原快照；
- 更新失败但已有知识的文档继续选择旧快照；
- 首次失败且没有可用快照的文档不进入 Build；
- 全失败/全 SKIP 时不创建无意义 Build，旧 Build 继续服务。

### 3. 每个 KB 只保留最新有效 Build

首次清理历史 Build 前，先用当前跨历史查询得到的有效文档—快照集合生成一个完整
checkpoint Build，并验证 serving 集完全等价。验证通过后才能删除旧 Build。

### 4. 检索只允许 KB 范围

```text
明确 KB 范围
→ 最新有效完整 Build
→ active document snapshots
→ v2 检索资产
```

删除空 `kbIds` 时回退域级 active release 的兼容分支；保留“无 KB 范围不允许检索”。

### 5. Snapshot 自动回收保留

```text
不再被最新 Build 使用
→ DEPRECATED
→ 等待 7 天
→ 再次确认未使用
→ 删除 snapshot 及派生产物
```

被最新 Build 继续选择的旧 snapshot 永不因年龄删除。指纹在 7 天窗口内重新命中可复活。

## 保留表的自动收敛策略

| 表/表族 | 最终保留策略 |
|---|---|
| `asset_source_batches` | 清无 Run、Build、link 引用的孤儿 batch |
| `asset_document_snapshots` | 现有 7 天 GC |
| `asset_document_snapshot_links` | 仅保留最新 Build 当前关系和 7 天恢复窗关系 |
| `asset_storage_objects` | 补 PG 登记与 MinIO 字节双向孤儿扫描 |
| `asset_parse_runs` | 每文档保留当前成功记录；最近失败短期保留 |
| `asset_builds` | 每 KB 最新一个 validated Build |
| `asset_build_document_snapshots` | 最新 Build 的全量选片 |
| Run 四表 | 当前 Build 来源 Run + 必要的最新失败/SKIP Run；其余整链删除 |
| v2 staging 八族 | 成功晋升清理；failed/cancelled 即时清；每日孤儿兜底 |
| `onenet_toc_cache` | 30–90 天 TTL/LRU |
| `kb_document_refs` | 清不存在/软删文档及非 active KB 的孤儿关系 |
| LLM 任务五表 | 现有 terminal 30 天 cleanup 接入每日任务 |
| `agent_llm_model_calls` | 7–30 天每日 TTL |
| `serving_query_logs` | 7–30 天 TTL，满足运维统计窗口 |

## 在线增量升级方案

### 固定原则

1. 不把 destructive DROP 永久塞入 `domain_schema_paths()` 或服务启动。
2. `deploy-build.sh` / `deploy-sync.sh` 继续负责传输和切换代码。
3. 独立、版本化、幂等的维护命令负责数据库 dry-run、迁移和验证。
4. 新建库 DDL 必须直接移除退役表；不能先创建再在每次启动时删除。
5. 所有唯一 Domain 数据库都执行；按 host/port/dbname 去重。
6. 默认不使用 `CASCADE`；发现未知依赖即停止。
7. DROP 不删除任何 MinIO 字节；对象字节由独立 GC 判断。

### 推荐维护命令

```text
python -m knowledge_mining.mining.maintenance.database_convergence --dry-run
python -m knowledge_mining.mining.maintenance.database_convergence --apply
python -m knowledge_mining.mining.maintenance.database_convergence --verify
```

命令放在 `knowledge_mining` 包内，确保进入现有增量包；根目录 `tools/` 不在同步面。

### 两阶段发布

#### 阶段 A：兼容代码

1. 删除所有退役表的生产读写和启动 bean。
2. 清理测试、统计、reset/export、文档和配置。
3. 从 PostgreSQL/SQLite 基线和启动链删除 CREATE TABLE。
4. 生成完整 checkpoint Build，补齐 active snapshots 的 v2 final 资产。
5. 部署并完成健康检查；旧表此时可暂时存在。

#### 阶段 B：一次性数据库清理

1. 进入维护窗口并暂停 Mining 写入。
2. 对全部唯一 Domain DB 和 LLM DB dry-run。
3. 检查行数、大小、依赖和活跃 legacy Run；非空非本体表默认先专项备份。
4. 本体数据按已确认决策允许全量删除；仍建议保留整库升级前备份。
5. 将 active domain release 数据迁入 KB checkpoint Build并验证等价。
6. 验证所有 active snapshots 已有 v2 units，需向量的已有 v2 embeddings。
7. 事务化、幂等、无 CASCADE 地删除 20 张退役表。
8. 清理无意义列、索引、CHECK 和状态枚举。
9. 重启并执行完整验收；重复执行迁移验证幂等。

### 回滚边界

- 阶段 A 可直接回滚代码。
- 阶段 B DROP 后不能直接运行旧版本；必须先用 rollback DDL 重建空表，或恢复升级前备份。
- 旧版 DDL若恢复会重新创建退役表，因此代码、DDL和数据库迁移必须作为同一版本单元管理。

## 验收清单

- 新建空库只创建目标 50 张真实启动表；
- 老库迁移后 20 张退役表全部不存在；
- 服务重启不会重新创建退役表；
- 上传、覆盖、下载、删除文档和删除 KB 正常；
- 全库挖掘、增量、全 SKIP、部分失败、全失败正常；
- checkpoint Build 与迁移前 serving 集一致；
- FTS、向量检索、结构导航、表格查询、来源回溯正常；
- MCP 与一张网正常；
- Snapshot、Build/Run、staging、LLM、query logs GC 可重复运行且不误删活数据；
- Java 三张表均保留并可正常读写。

## NON-GOALS

- 不保留本体研究功能的空壳数据库面。
- 不保留域级 release 兼容入口。
- 不为未来可能功能预建表。
- 不在本次把 v2 八族或 Java 检索范式强行合表。
- 不把数据库删除隐藏在普通服务启动中。
