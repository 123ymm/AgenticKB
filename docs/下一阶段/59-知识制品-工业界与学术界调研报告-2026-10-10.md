## 一、执行摘要

1. **方向已被外部世界强力验证。** 过去 12 个月，工业界与学术界同时收敛到 39号（2026-09-08）提出的同一判断——"把 Agent 反复进行的查找、整理、对齐、判断提前到知识建设阶段完成"。Pinecone 在 2026 年的产品里直接使用了同名词 **knowledge artifacts**（"typed, governed information object constructed for a specific task"）；Sierra 的 τ-Knowledge 基准用数据证明：即使把正确文档直接递给 Agent，最强模型也只有约 40% 通过率——**瓶颈在知识组织，不在模型**。
2. **"知识制品"的载体格式已事实标准化。** Anthropic Agent Skills（SKILL.md 目录格式）2025-12-18 成为开放标准，截至 2026-08-20 已有 11 个客户端原生支持；2026-08 的 Agent Plugins 1.0.0 把 Skills 与 MCP 服务打包为可移植插件。制品若兼容此格式，即免费获得整个生态的入口。
3. **制品的交付通道已标准化。** MCP 官方 Skills Extension（SEP-2640，stable，基于 2026-07-28 版基协议）定义了 `skills/list`、`skills/get`、`resources/read` 的 skill 服务方式与安全模型——我们的 `mcp_server` 天然是这个通道的候选实现。
4. **学术界已形成"编译→评测→精炼"的完整方法论。** Corpus2Skill（编译语料为导航技能树）、WiCER（CEGAR 式迭代编译修复"压缩丢事实"）、Training a Knowledge Base（把知识库当作在问答对上"训练"的非参数模型）、Knowledge-as-Skill（SKILL.md+OKF 三层组织）分别在编译、评测、反馈三个环节给出了可复现的方法与数字。
5. **编译有收益也有明确边界。** Corpus2Skill 的 11 数据集实验：单领域原子文档语料显著赢（最高 +0.135 F1），开放域/同构表格语料反而输（-0.05~-0.17）——与 54号"按任务选择知识形态、不把所有资料转成同一种结构"的判断完全一致，且给出了可操作的选型判据。
6. **价值量级有了公开基准数字。** Pinecone Nexus（2026-08-06 GA）在 τ-Knowledge 上以知识层拿下榜首：47.4% vs 最强裸模型 46.4%，单任务成本降 74%（$1.45→$0.53）；GPT-5.2 加知识层 +12% 准确率、-80% 成本，工具调用 42.5→17.7 次/任务。"是知识，不是模型"（Pinecone 官方结论）。
7. **我们 54号总纲的治理要求严于业界公开水平。** 四种版本分离、来源链路、专家校准不可静默覆盖、反馈只形成变更候选——这些在 Nexus 公开材料中只有部分对应物（per-field citation+confidence、PII 标注、访问控制在检索时执行）；学界更是普遍缺失。这是差异化的机会，也是实施复杂度所在。
8. **内部最大缺口：对象层与制作链均为零代码。** 制作链：48/50号已设计完整"制品登记→草稿→试用→发布→反馈"闭环（含 MCP 制作工具、任务票据、DSH 适配器），但仓库 grep 六关键词**零命中**，DSH 镜像已构建未联调。对象层（§6.6/§6.7 定稿的平台必需层）：完全没有——而 NewSFCGraph kg 服务（§3.7）提供了可吸收的现成实现（八张表骨架/有效投影/挂载状态机，22,938 对象实测运行）。
9. **存在一处必须先调和的架构冲突。** ADR-0001 D10 把 Knowledge Artifact 锚定为 `document_snapshot_id` 之下的场景化子资产；而 48/49/50号的制品是跨文档、独立发布修订的领域级对象。两者未见调和性 ADR——实施前必须补，否则表结构无法定。
10. **落地路径（2026-10-15 定稿，五阶段路线详见 §七末）**：核心架构 = 知识四形态（材料/证据/对象/制品）+ **对象层为横切身份平面**（§6.6-6.8，经三路对抗审查定稿）；实施顺序 = 架构定稿（P0 ADR）→ 吸收 kg 骨架建对象层 → wiki 流水线最小闭环（输出落点=对象层）→ 表格确定性抽取 → 制品生命周期与消费面收敛；对外出口吃标准红利（SKILL.md/OKF 导出零协议风险，MCP Skills Extension 二期评估）；**通用化验收标准 = 第二个域零代码接入**。全部零新依赖（§6.4）。

## 三、工业界现状（2025Q4–2026Q3）

### 3.1 Agent Skills：从单厂功能到开放生态

时间线（均为可点击来源）：

- **2025-10-16** Anthropic 发布 Agent Skills——"用文件与文件夹构建专用 Agent"，`SKILL.md` 为入口（[Anthropic Engineering](https://www.anthropic.com/engineering)、[anthropics/skills 仓库](https://github.com/anthropics/skills)）。
- **2025-12-18** 成为开放标准，发布规范与 SDK，任何 AI 平台可采纳（[Strapi 2026-02-10](https://strapi.io/blog)）。
- **2026 年中** 生态成型：目录、市场、构建者网络（[Agentman 2026-06-24](https://agentman.ai/blog)）。
- **2026-08-06** Agent Plugins 1.0.0：开放、厂商中立的插件规范，把 Skills 与 MCP 服务打包为可移植插件（[Google Developers Blog 2026-08-06](https://developers.googleblog.com)、[解读 2026-08-11](https://www.getclaudeskills.com/Blog)）。
- **2026-08-20** Skills Board 兼容矩阵确认 **11 个客户端**原生读取 SKILL.md（[skillsboard.sh](https://www.skillsboard.sh/resources)，2026-09-03 更新）。

规范要点（[agentskills.io/specification](https://agentskills.io/specification) 原文核对）：

- 技能=目录：`SKILL.md`（必需）+ 可选 `scripts/`（可执行代码）、`references/`（按需文档）、`assets/`（模板/数据）。
- frontmatter 字段：`name`（≤64 字符，小写-连字符，须与目录同名）、`description`（≤1024 字符，"做什么+何时用"）、`license`、`compatibility`（≤500）、`metadata`（任意键值）、`allowed-tools`（实验性）。
- **渐进披露三级**：元数据约 100 tokens（启动即载）→ 正文建议 <5000 tokens / <500 行（激活时载）→ 资源文件按需载。
- 官方校验工具 `skills-ref validate`（[agentskills/agentskills](https://github.com/agentskills/agentskills/tree/main/skills-ref)）。

**对本项目的含义**：54号§五.4"可执行的方法"类制品（作业流程/模板/Skill/场景知识包）与 SKILL.md 结构几乎一一对应（`references/`≈来源锚点文档、`assets/`≈模板与对照表）；一张规格矩阵导出为"技能目录+资产文件"即可被 11+ 客户端消费。

### 3.2 MCP 2026-07-28 与 Skills Extension：制品的标准交付通道

MCP 基协议 2026-07-28 版关键变化（[官方 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)、[发布公告](https://blog.modelcontextprotocol.io/posts/2026-07-28/)）：

1. 协议无状态化：取消 `initialize` 握手与会话头，版本与能力随每个请求的 `_meta` 携带。
2. `resources/subscribe` 被 **`subscriptions/listen`** 取代：单一长连接推送服务端变更通知（toolsListChanged/resourcesListChanged 等）——**这是"制品发布新修订后主动通知 Agent"的现成协议机制**。

**Skills Extension**（[SEP-2640](https://modelcontextprotocol.io/seps/2640-skills-extension)，[stable 规范](https://skills.extensions.modelcontextprotocol.io/specification/stable/skills)，[概览](https://modelcontextprotocol.io/extensions/skills/overview)）：

- 扩展 ID `io.modelcontextprotocol/skills`，基于 2026-07-28+ 基协议，构建在 Resources 原语之上。
- 三个方法：`skills/list`（必需，分页+可缓存）、`skills/get`（按 URI 取单个技能）、`resources/directory/read`（可选，列目录）。
- Skill 条目 = `uri`（约定 `skill://<路径>/SKILL.md`）+ `frontmatter`（原样透传）+ `resources[]`（每个文件带 `sha256 digest` 与 `size`，或声明 `"dynamic"`）。
- 规模上限：**每技能 512 文件 / 16 MiB**；身份 = 宿主标签+URI 二元组。
- 安全模型：MCP 下发的技能按**不可信内容**处理（与本地技能不同）；`allowed-tools` 默认忽略；用户审批与资源内容集绑定，内容变更即失效。

**对本项目的含义**：`mcp_server` 若实现该扩展，已发布制品即以标准技能形态对 Agent 可见（列表→按需读取→回溯原文走现有 `get_knowledge`）。注意我们当前 fastmcp 3.4.7（`mcp_server/server.py:187` 注释佐证）对 2026-07-28 基协议与 extensions 机制的支持程度**需实测**——这是二期决策项，不是拦路虎（纯文件导出不受影响）。

### 3.3 Pinecone Nexus：知识引擎的完整产品化

Nexus 2026 年 5 月亮相、**2026-08-06 GA**（[GA 博文](https://www.pinecone.io/blog/pinecone-nexus-generally-available/)、[官方新闻稿](https://www.pinecone.io/newsroom/general-availability-of-pinecone-nexus-proves-knowledge-drives-real-outcomes-for-agentic-ai/)、[产品页](https://www.pinecone.io/product/nexus/)、[The Ceiling Was Never the Model](https://www.pinecone.io/blog/the-ceiling-was-never-the-model/)）。架构与我们的概念高度同构：

| Nexus 概念 | 描述 | 对应 54号概念 |
|---|---|---|
| **Knowledge Artifact** | "原子单元：为特定任务/结果构造的、带类型的、受治理的信息对象" | 知识制品（定义几乎逐字一致） |
| **Context** | 为一个团队/角色/工作流策展的制品集合 | 领域/场景知识包 |
| 编译层 | "编码代理编译：assemble→reason→structure→compiled artifacts"；**由数据变化触发更新**，非查询触发 | 挖掘管线 + 制作实例（链路A） |
| Manifest | 描述工作所需实体、关系与答案形态 | 制品"用途与验收"（八类内容之②） |
| KnowQL | 声明式查询：Intent/Filter（含访问控制）/Provenance（**字段级引用+置信分级**）/Output Shape/Confidence/Budget | 制品的结构化消费（我们的 st_ 表格查询协议是雏形） |

实测数字（τ-Knowledge，见 §5.6）：Nexus 知识层 + GPT-5.2 = **+12% 准确率、-80% 成本**；+ GPT-5.5 = 同准确率 -77% 成本；工具调用 42.5→17.7 次、模型调用 81.7→42.6 次/任务；优势在 97 任务中的 96–97 个上成立。单次 KnowQL 查询 0.5K tokens/50ms vs agentic RAG 12K tokens/~4s。治理：字段级引用+置信度、入库时 PII 标注、检索时执行访问控制、部署在客户自己的云。

**边界**（公平记录）：Nexus 不解决"自动发现企业全部业务场景"（需人员给出工作目标与评价任务，39号§三.1 已指出）；其编译细节不开源，可借鉴的是产品形态与验收口径。

### 3.7 本地工业参考实现：NewSFCGraph 知识治理服务（2026-10-13/14 评估）

**是什么**：为云核心网（5GC）配置治理建的"节点-挂载-关系"知识关联管理服务（FastAPI+PG+Vue，2026-10-12 定独立部署架构），把 13 万命令级 md 图谱与 AIMML 结构化规则库桥接为统一索引，经 REST + 只读 MCP（`search_knowledge`/`get_knowledge`/`get_related_knowledge`，前两名与我们工具同名）供人和 Agent 消费。八张表（kg_types/objects/sources/mounts/relations/catalog/import_jobs/changes）；15 个配置领域类型；已实测导入 **22,938 对象**、45,401 条关系待确认；AIMML 侧 466 万行语法规则表仅测试 schema 接入。交接文档：`D:/mywork/KnowledgeBase/NewSFCGraph/知识治理/AgentKB-通用知识关联管理需求与实现交接.md`。

**核心价值：它已实现我们只写在纸上的机制**（逐行核对过代码）：

| 我们的设计（48-54号） | 它的实现 | 成色 |
|---|---|---|
| 来源锚点 | kg_mounts 挂载状态机（active/detached/unverified，**同步永不复活人工解除**）+ kg_sources 内容哈希快照 | 已运行 |
| 人工校准不可静默覆盖 | manual 覆盖 JSON + **参数墓碑**（人工删除跨同步持久）+ 全部 UPSERT 带 WHERE manual=false 守卫 | 已运行 |
| 预览→发布门禁 | import_jobs 两阶段：对象修订/类型修订/版本目录/文件哈希四重 stale 校验，apply 单事务 | 已运行 |
| 字段级溯源 | field_states 三元组（来源值/人工值/有效值）+ 定位器 | 已运行 |
| 制品修订并发 | revision 乐观锁 + 审计必填 reason | 已运行 |
| 版本归一 | kg_catalog 海外↔国内版本映射（449 条权威桥） | 已运行 |

**为什么对象层对 Agent 消费是质变**（以"查 MOD_SNSSAI 命令的参数/适用网元/关联特性"推演）：纯检索 = 5-10 次调用 + 从散文重建表格 + 版本混淆（τ-Knowledge 口径下引用错版本直接零分）；对象层 = 1-2 次调用拿到三源合一的有效值 + 关系（带置信四级）+ 字段级溯源。**一句话：检索平台回答"哪里说了什么"（给你地方），对象层回答"这个东西是什么、和什么有关系、现在有效的是什么"（给你东西）。** 诚实的边界：长尾文档问答、无稳定身份语义的一次性材料、单源无版本内容——不需要对象层（kg 交接 §1.2 亦拒绝全对象化）。

**已知限制**（交接自认+审查发现）：片段级/行级挂载未实现（参数不可独立寻址，objects.py 对 CommandParameter 直接 422）；产品版本在 kg_catalog 非统一对象图；466 万行未真接（2 万 md 成功≠百万级）；nf/version 固定列、3 张表名、VERSIONED 集合硬编码；无用户体系；对抗审查发现残留缺陷——**非 manual 的"已拒绝"关系会被 UPSERT 复活为"待确认"，拒绝墓碑需要独立机制**（吸收时须修）。

| DTBench / TableSeek | [KDD](https://dl.acm.org/doi/abs/10.1145/3770855.3817516) / [arXiv:2609.34157](https://searcharxiv.org/abs/2609.34157) | 文档→表格抽取基准 / 异构表格语料上的保结构取证 |

**对本项目的含义**：Executable Schema Contracts 的三个机制（闭世界字段目录、确定性结构分析、单调扩展）几乎就是 54号§六"内容定义与校验"+"最小本体"的实现蓝图——**字段目录先于抽取、schema 只扩不收、主键/单位确定性识别**；TASER 证明"抽取→发现 schema 缺口→修订 schema→再抽"的闭环值得做进制作工具链。

**"可判的规则"的外部坐标（勘误说明）**：规则本身不是外部空白——规则引擎/决策表是数十年成熟工业（OMG DMN 标准、Drools、Open Policy Agent/Rego、JSON Schema/CEL 校验、LLM guardrails），本报告引用的材料里也遍布其形态：Executable Schema Contracts 的确定性谓词与访问控制、τ-Knowledge 的"严格策略遵循"判分（[arXiv:2603.04370](https://arxiv.org/html/2603.04370)）、B5G 配置论文的参数定义表（类型/取值范围/依赖关系，[arXiv:2606.01222](https://arxiv.org/html/2606.01222)）。真正外部没有先例的，是**把规则当"有出处、可校准、按版本发布"的知识制品来运营**：规则引擎界假设规则由工程师手写为代码（无来源链与专家校准生命周期），知识检索界只交付文本证据（规则埋在文档里由 Agent 自行阅读），两者尚未合流。**2026-10-10 讨论裁定（用户拍板）**："规则"不再作为独立制品类型——**"规则就是一种数据，只在被使用时才被当作规则"**。制品分类收敛为两型：**可查的数据**（表格、对象卡、对照表、**约束表**、最小本体；约束性作为数据制品的用途标签，如"描述性/约束性"）与**可执行的方法**（流程、模板、Skill 包、场景知识包）。裁定依据：①外部两大制品体系（Nexus 的摘要/结构化抽取/图谱、Agent Skills 的说明书+脚本+参考+资产）均无"规则"顶层类型；②规则的两种真实归宿分别落入两型——当查询用即约束对照表（数据），当执行用即检查器（工具/代码，非知识）；③54号§十本就规定规则首期只"以结构化正文形式进入"；④云核 53 万核查规则的现存形态即**可查询数据记录**，恰为"规则=数据"的内部实证。上段所述差异化空间相应改为"**约束类数据制品的治理与交付**"；41/54号原文的三分类保留为历史记录，后续文档以两型为准。

### 4.7 制作工艺深度：四个关键问题的证据（2026-10-10 补充检索）

**Q——任务从哪发现？** 四来源并用：①人填任务说明（Nexus：源数据+task spec+eval set 三输入，粒度由任务推导——同源数据按角色产出不同制品，[官方机制文](https://www.pinecone.io/learn/how-knowledge-engines-work/)；manifest 格式与评价集建法未公开）；②**失败驱动**——DDC（[arXiv:2603.14057](https://arxiv.org/pdf/2603.14057)）借 TDD 思想：给 Agent 真实问题→失败暴露知识缺口→只策展最小所需知识，20–30 轮问题循环收敛一个岗位的知识库（实测 9 轮→46 实体）；③使用数据反推（查询日志/零结果——我们 56号账本即现成数据源）；④执行经验沉淀（SkillWeaver [arXiv:2504.07079](https://arxiv.org/abs/2504.07079) 三阶段：提案→试做+奖励评估→合成接口+自动测试打磨；SkillX [arXiv:2604.04804](https://arxiv.org/html/2604.04804)；轨迹不可直存，0.3GB/条）。

**Q——代码抽取还是 Agent 理解？** EVAPORATE（[arXiv:2304.09433](https://arxiv.org/abs/2304.09433)，VLDB'24）实测判据：**~40 份文档是成本交叉点**；代码生成成本只随字段数增长不随文档数（10k 份省 110×）；单生成函数 -13.8 F1 且 40% 低于 25% 准确率→多候选函数+弱监督集成（Code+）后反超逐份理解 +12.1 F1（22%）。进阶：MOAR（[VLDB'26](https://www.vldb.org/pvldb/vol19/p3062-shankar.pdf)）把该选择自动化——code_map/code_filter/code_reduce 代码合成指令、sample/extract 省钱算子、输出准确率-成本帕累托前沿、30+ 改写指令；物理参数从不问 LLM 而是样本实测选出。铁律：**先定 schema 再抽取**（schema 识别只需抽样）。

**Q——大语料规模化？** 六手段（各有实测数）：分层摊薄（聚类零 LLM+簇级摘要，Corpus2Skill 6,221 篇 19.5 分钟、5 万篇结论不变；Beever Atlas 余弦聚类合并零 LLM 成本）；生成代码可复用（数据变更重跑零 LLM 成本）；批处理 API 半价（map-reduce 两段，10 万份几十美元，[OpenRelay](https://openrelay.inc/batch-inference-api/document-summarization)）；增量编译（KaaS 只重编变更且 merge-not-replace、inite-brain 500 份/批自链+抽取缓存+chunk 哈希省 95%、fluidzero O(delta)）；先去重（砍 10–25% 体量）；吞吐基线（fluidzero：归一化 500 页/分/worker，100GB≈百万页 8–12h@4GPU+8CPU）。**反面教材**：bobs-big-brain（[PR#145](https://github.com/jeremylongshore/bobs-big-brain-compiler/pull/145)）726 份摘要塞单次 64K 调用被静默截断、整库只出 3 个概念——大批量必须分批+跨批合并+幂等 UPSERT+产物量校验。工程编排现成模式（KaaS）：队列+租约（300s 心跳续约/超时回收）+断路器（5 失败熔断 30s）+SSE 进度。

**Q——"SKILL 让 Agent 转"是否主流？** 否。实测（[jerryjliu/agent_extract_experiments](https://github.com/jerryjliu/agent_extract_experiments)，LlamaIndex 作者）：Claude Code 捆绑 llama-extract 技能做抽取，计费后总成本为 Agent 自读的数倍、准确率分领域。该模式仅适合 ≤40 份的原型；量产工艺是"Agent 写程序（schema+代码+校验），程序跑语料"。**对 50号 的含义：DSH 试点 3–5 份文档落在逐份理解区，作为工艺验证合理；量产须换代码生成/管线工艺——实施计划须明确两阶段关系。**

### 4.8 LLM Wiki 型制品：构建工艺（2026-10-13 拍板为最高优先级）

**定位与页结构**：Karpathy 构想（[gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，39号已引）——原始资料不可变 + LLM 持续维护派生层。页的收敛形态（[LLM-Wiki 论文](https://arxiv.org/abs/2605.25480) + [Knowledge-as-Skill](https://arxiv.org/abs/2609.25991)）：标题 + 摘要 + **带来源锚点的结构化事实** + 双向链接（含矛盾页）+ 生命周期元数据。与表格制品的本质区别：**结构不是预设 schema 而是长出来的**（页面会分裂/合并/改名/互链），核心难题是页面组织一致性而非抽取。

**五道工序（全部来自真实系统）**：

| 工序 | 做法 | 出处 |
|---|---|---|
| ① 原子化+聚类 | 原始内容→原子事实→余弦聚类（纯代码零 LLM）→主题/概览；**LLM 调用单位是簇不是文档** | [Beever Atlas](https://docs.beever.ai/atlas/getting-started/how-it-works) |
| ② 页面写作 | 写前先**分类**：判断与哪些已有页重叠→**合并不新建**（防页面爆炸）；长文先便宜模型压缩再抽 | [KaaS](https://bybit-exchange.github.io/kaas-doc/concepts/compile-pipeline.html) |
| ③ 链接与矛盾 | 四个跨源 pass：extract/synthesize/**contradict**/**gap**（矛盾页与缺口页为显式产物）；Error Book 记账断链/引用错误/无据内容/跨页矛盾，**确定性检查先行、LLM 只复核** | [bobs-big-brain](https://github.com/jeremylongshore/bobs-big-brain-compiler/pull/145)、LLM-Wiki 论文 |
| ④ 诊断探针 | 拿问题让 wiki 与原文分别回答，差异=丢事实→标记保留→重编译；**盲压灾难失败率 53–60%，1–2 轮恢复 80%** | [WiCER](https://arxiv.org/abs/2605.07068) |
| ⑤ 候选提交 | 候选≠知识；提交时按（实体,属性,值）合并、置信度取最大、冲突四态（拒绝/佐证/取代/竞争并存）；500 份/批自链+未变文本命中抽取缓存 | [inite-brain](https://github.com/inite-ai/inite-brain-service/blob/main/docs/document-pipeline.md) |

**工程底座**（稳定性真正来源）：分批（25/批+跨批按归一化标题合并——bobs 静默截断教训：726 份塞单次调用整库只出 3 个概念）、幂等（稳定 ID+UPSERT）、租约+断路器（KaaS 默认参数：租约 300s 心跳续约/超时回收，5 次失败熔断 30s）、页面缓存（Atlas：wiki 读取零 LLM 成本）、内容哈希增量。

**流水线 vs Agent 平台判别式**：随语料更新可重跑、结果稳定、成本低 → **流水线**；一次性交互起草+专家在环 → **Agent 会话**。五个 wiki 构建系统全部是确定性编排流水线，无一自主 Agent 循环；Agent 只出现在优化期（DocETL/MOAR 改写管线、Nexus coding agent 写管线代码）与一次性草稿（50号 DSH）。**结论：LLM Wiki 的稳定构建不需要通用 Agent 平台**。落回本系统：wiki 编译器可作为新管线挂现有挖掘侧骨架——聚类/链接检查=代码，LLM 工位走 llm_service 异步通道，快照/版本/增量指纹复用，零新依赖。

**最小区间启动建议**：一个同构目录语料跑通五道工序；必带 Error Book + 诊断探针（20–50 个真实问题）；验收只看两个数=**丢事实率**（探针测）+ **页面重跑稳定性**（同语料重跑页面 diff 应≈0）；不达标不扩语料范围。

### 6.3 缺口清单（按建议优先级）

1. **P0｜ADR 调和**：D10（Snapshot 子资产）vs 48/50号（跨文档领域级制品）——不出新 ADR，制品表结构无法定。这是所有实施的前置。
2. **P0｜制品登记与修订状态机**：制品 ID、负责人、状态（草稿/试用/发布/停服）、修订号、四种版本分离的落地表。54号§十第一行。
3. **P1｜来源锚点表**：制品字段/段落/对象 → 文档+章节+快照版本的直接引用（strpos/定位协议已有可借鉴实现）。
4. **P1｜内容形态首版**：LLM Wiki 型（主题页/对象页，2026-10-13 拍板为首选，工艺见 §4.8）+ 表格（复用 st_ 协议，**确定性代码构建**）+ Markdown 正文 + 最小本体定义（54号§十第二行基础上的更新）。
5. **P1｜试用与评测门禁**：代表题集+诊断探针+新旧对照（检索 vs 制品）落到 A4。
6. **P2｜制作链**：50号 DSH 试点 T0–T6（get_creation_context/submit_creation_result/任务票据/适配器）。
7. **P2｜反馈闭环**：账本信号→变更候选（54号§六.5 信号表 SQL 化）。
8. **P3｜标准出口**：SKILL.md 导出（纯文件，零协议风险）→ MCP Skills Extension 接入（先实测 fastmcp 3.4.7 对 2026-07-28 基协议支持）。

### 6.5 数据类制品的六个设计问题（2026-10-12/13 讨论定稿）

1. **形态清单（不止表格）**：结构化表格、实体档案/对象卡（跨文档合并，Nexus "cross-document entity profiles"）、关系图（dependency graphs）、语义层（表+字段含义+关系+反模式+示例，Nexus "analytics semantic layers"）、决策框架（从政策文档蒸馏）、主题页/摘要（wiki 线）、导航树（Corpus2Skill）——前六种属"可查的数据"型。
2. **交付=查询不下载**：小→整读；中→结构化查询（现有 st_ 协议即此通道：select/where/order_by/limit/cursor）；大/复杂→声明式一次调用（KnowQL 形态：要什么+条件+引用+输出形状+预算，0.5K token/50ms vs 多轮检索 12K/4s）。两个必备细节：返回带**字段级引用**（值→文档/章节/版本）；**权限在查询时执行**。本质=只读数据库视图+逐字段溯源。
3. **发现=目录常开+内容按需**：每制品一张说明卡（名称+描述+适用范围，~100 token）常驻 Agent 上下文；制品多则对说明卡做检索。SRA 实证（5,400 实例+26,262 技能库）：正确制品被检索到后 Agent 仍常不知是否/何时使用→**说明卡必须写"何时用/何时别用"**。Nexus 补充做法：按角色预分组收窄可见范围。
4. **持续构建=生长型制品**：同一任务定义+同一管线跑新文档→实体对齐/去重→合并（每行带来源：来自哪份文档哪节哪版本）→schema 只扩不收（单调扩展）→冲突标出专家裁决（人工校准不被静默覆盖）。合并机制详见 §4.7/§4.8。
5. **海量制品服务**：语义层挡在裸表前 + 分页游标（st_ 已有）+ 聚合摘要层（先查摘要再下钻）+ 双索引（精确条件走数据库索引、模糊查找走向量索引）。
6. **"数字化→智能化"三层+边界**（用户提出，调研证实）：**语义层**（用得对：字段含义/单位/常见误用/示例）、**判断层**（支持决策：约束数据+决策框架）、**学习层**（错了能改：[Training a KB](https://arxiv.org/abs/2608.21829) 把库当非参数模型按问答对编辑）+ 第四形态**接口化**（[SkillSmith](http://arxiv.org/abs/2605.15215v1)：制品编译为最小可执行接口，token -57%/耗时 -51%）。共识边界：**制品不预生成最终答案**——智能化是让 Agent 查得准/用得对/错了能改，不是替 Agent 思考。

### 6.6 知识形态与平台能力模型（2026-10-14 讨论定稿）

**关键澄清**：知识库/挖掘/制品/管理不是四层知识，是**平台能力名**。知识本身按形态分四层（本体轴），平台按能力分六项（平台轴）——两轴分开后概念不再打架。

**知识四形态**（方法论定义，与场景无关）：

| 形态 | 定义 | 特征 | 我们对应 |
|---|---|---|---|
| L0 材料 | 一切未加工来源，知识的**载体** | 不可变（快照+哈希）、带权限版本 | asset_documents+snapshots（已有）；结构化数据源接入待扩展 |
| L1 证据 | 材料解析后的**可引用片段** | 精确位置指针（能回 L0） | retrieval units / asset_table_cells（已有） |
| L2 语义对象 | 被赋予**身份**的知识单元——知识第一次成为"东西"而非"地方" | 稳定 ID、多源合成有效值、对象间关系 | **缺**；kg 服务为可吸收实现（§3.7） |
| L3 知识制品 | 面向**任务**组织的**发布单元** | 用途+验收+修订+发布生命周期 | **缺**；本报告主线 |

**分层是形态谱系不是强制流水线**：制品可直接从 L1 组合（不经过对象化），对象可直接从材料抽取（表格一行即对象）。两个贯穿面：**治理面**（溯源/有效值/人工修正/生命周期/审计）与**交付面**（检索 L1/对象读取 L2/结构化查询 L2-L3/导出 L3，web+API+MCP 同源），作用于所有层。

**平台六能力**与现状：①接入保管（有）②加工管线（L0→L1 有，L1→L2/L3 缺）③身份与关联（缺，吸收 kg）④治理（部分）⑤交付（有）⑥运营（账本有数据、闭环缺）。

**业界谱系**（"结构化×非结构化统一关联"的实证）：Executable Schema Contracts（schema 作为合同统一构建与检索，[arXiv:2606.05415](https://arxiv.org/abs/2606.05415)）、inite-brain（文档事实与 API 事实同一裁决）、Nexus（混合源编译三形态）、kg 服务（md+AIMML 靠对象身份+挂载桥接）；我们 54号五层是其业务语言前身（第③层"语义资产层"=L2+L3，当时未拆分）。

**统一管理的含义：统一动词，不统一名词**——平台统一提供六个管理动作（**进**接入/**认**身份核验/**联**挂载关系/**改**人工修正保护/**发**制品生命周期/**退**停用回收）+ 治理状态机；内容格式无限多样，靠"域类型包"（云核 15 类=第一个包；硬件/一张网/Wiki 各一个包）配置进。

### 6.7 对象层定位：横切身份平面（2026-10-14 三路对抗审查定稿）

用户模型（"对象层放最顶上索引制品原子，所有知识经对象层关联"）经架构/业界先例/工程断裂三路对抗审查：**总体成立且有强先例**——Wikidata（1.23 亿 item 统一关联 300 语言维基；Phase I 把文章互链收编为对象关系="互链继承"的亿级一次性先例）、Palantir Foundry Ontology（官方定位"本体在数据资产之上"）、MDM 黄金记录/survivorship（"对象不只是指针"的最早工业谱系，kg 三层值即其知识库翻版）、kg 服务（本地实证）。该模式属**关联/治理谱系**（semantic layer + ontology + entity layer + MDM 四谱系拼成），区别于 feature store 类生成谱系。Corpus2Skill/Knowledge-as-Skill **无对象层**——此步即差异化所在。

**三处修正**（按字面实现会断）：

1. **对象≠纯指针**：人工修正需要家（纯指针层无处放"不被重导覆盖"）、多源合成不能推给每个 Agent。对象=**身份+关系+有效值投影**（活跃挂载∪人工覆盖，运行时合成，内容不复制）。
2. **非全对象化**："可寻址≠是对象"；升格判据=需要"自己当关系端点/自己的生命周期/被独立治理"之一。kg 对 CommandParameter 直接 422 拒绝即此原则。
3. **互链"继承"改为单向抽取管道**：md 引用是证据，抽取成候选关系（带 source_key/置信四级/待确认），人裁决后对象层成为查询唯一事实源；md 永不回写（kg 逻辑网元双事实源不同步是其前车之鉴）。

**修正后的定位**：对象层是**横切身份平面**——不在制品之上也不在其下；向下用挂载/锚点连到不可变证据与材料，向上被制品单向引用；两条入口共存（存量内容自下而上导入+人裁决；新建制品 manifest 自上而下声明+编译登记），进同一身份空间。

**五条工程硬要求**（进入实施验收清单）：

| # | 要求 | 断裂场景 |
|---|---|---|
| 1 | **原子身份是过程不是字段**：wiki 页分裂/合并/改名走"身份再解析工序"（对齐+别名+墓碑）；行地址=(表, 业务主键)，禁止行号/内容哈希；重编译幂等="同语料重跑 diff≈0"门禁 | **静默错链**（行重排后对象指向别的命令的取值范围——唯一可能直接产生生产事故的断裂点） |
| 2 | 指针失效走状态机不物理删；我们的 7 天快照 GC 回收前必须检查入链引用计数 | 制品停用/重发布时链接悬空或被偷换 |
| 3 | **自动确认是默认路径**（显式证据+唯一解析才自动过），消费侧允许读"待确认"但带置信标签（**带置信度的临时真相**）；队列按使用信号排序（56号账本） | 13 万对象≈26 万待确认关系，人工 200 条/天=3 人年，队列积压成坟场 |
| 4 | 守卫谓词（WHERE manual=false 类）与 manual 标志进数据模型第一天；吸收 kg 时补修"已拒绝关系被 UPSERT 复活"缺陷 | 后补=重写全表；治理信任崩塌 |
| 5 | P0 ADR 调和前置（§七.3）：制品=独立顶层对象+保留"回指原子来源"铁律——kg_objects 即活样本 | 表结构无法定 |

### 6.8 通用平台架构与云核沉淀路径

```text
┌──────────────────────────────────────────────────┐
│ 制品层：Wiki 制品集 / 表格制品（发布单元，54号生命周期）    │
│   制品中的值 → 单向引用对象（编译期登记，revision 固化）    │
└──────────────────▲───────────────────────────────┘
╔═══════════════════╧════════════════════════════════════╗

║   ｜关系=唯一查询事实源｜有效值投影（运行时合成）                ║
║   入口A 自下而上(存量导入→抽取→人裁决) / 入口B 自上而下(manifest) ║
╚═══════╤══════════════════════════════╤═══════════════════╝
        │挂载/锚点(md/表行/片段)   证据层(L1：切片/表格行——已有)
        ▼                        材料层(L0：不可变快照——已有)
  贯穿：治理面｜交付面(web+API+MCP 同源)｜运营面(账本→缺口→建设)
  长尾内容停留 L0/L1 不强制对象化；覆盖度与缺口显式可见
```

**人与 AI 分工：机器提议、人裁决**——量级现实（22,938 对象已积压 45,401 待确认）决定人不可能组织全部；人定类型/身份规则/归属约束/验收标准/裁决冲突，机器做导入解析/批量抽取/关系推断出候选（带来源置信），AI 串联是**默认通道而非预留入口**，靠状态机+置信四级+审核队列兜住。业界（WikiSkill"经验→提案→独立评测→采用"/SkillWeaver 三阶段/54号"反馈只形成变更候选"）全是此分工。

**云核沉淀=骨架归平台、领域归配置包**：八张表机制/有效投影/状态机/两阶段导入归平台（写一次）；15 类型/nf·version 身份列/3 张表映射/VERSIONED 集合/逻辑网元派生规则归"云核配置包"。三个通用化改造（kg 自认）：类型从代码定义改页面配置（身份规则参数化）；来源 kind 从 CHECK('md','aimml') 开放为可注册读取器；导入方案（表→对象映射）配置化。**通用化验收标准只有一条：第二个域零代码接入**（建议站点硬件或一张网验证）。

1. **制品对外格式是否采纳 SKILL.md/OKF 双标准？**
   推荐：是。理由：Knowledge-as-Skill（2609.25991）证明 OKF frontmatter+SKILL.md 三层组织在企业语料上当前最优（WixQA Factuality 0.889）；采纳即免费获得 11+ 客户端生态（Skills Board 2026-08-20）。代价：frontmatter 字段约束（name≤64 等）需纳入制品命名规范。
2. **首轮落地组合（2026-10-13 拍板后已收敛大半）**：
   首轮主线 = **LLM Wiki 流水线最小闭环（§4.8）+ 表格确定性代码抽取（EVAPORATE 路线）**；"出口快赢"（已挖好的结构化内容按制品+SKILL.md 导出）作为低成本并行验证（Corpus2Skill 输赢判据提示不是所有库都值得编译，出口可先试出哪些内容真被高频使用，账本可度量）；**50号 DSH 从"首个试点主链路"调整为交互式修订/一次性草稿工具**（依据 §4.8 判别式：随语料生长的资产走流水线，人在环草稿走 Agent 会话）。
3. **ADR 调和方向**：制品作为独立顶层对象（跨文档、独立修订）+ 必须携带 Evidence Link 指向原子快照元素（保留 D10 的回指铁律，放弃"制品从属于单一 Snapshot"）？
   推荐：是——这保留 ADR-0001 的治理意图（可回源、READY 后禁追加），同时兼容 48/50号跨文档模型。
4. **试用评测门禁**：是否把"代表题集+诊断探针+新旧对照（检索 vs 制品）"设为制品发布的硬门禁（54号§五.6 已原则性要求）？
   推荐：是，且对照口径抄 τ-Knowledge：按最终任务状态判分、"引用了错误版本政策得零分"。
5. **反馈信号源**：是否首期就把检索记录账本（56号）接到"高频回原文/零结果/缺口"统计（54号§六.5）？
   推荐：是——数据已在库里，SQL 化即可，为下一轮"编译什么"提供依据（Training a KB 的思想）。
6. **第二个试点候选**（40号遗留：IP 配置行为/云核配置生成/站点约束表——新口径下原"站点规则包"即约束类数据制品）：
   参考：外部热度最高的是配置生成（§五，5 篇 2026 年论文+3GPP SA5 动向）；我们内部资产最厚的是云核（79 万命令记录+53 万核查规则——新口径下即现成的约束类数据资产）。若要"快出价值证明"选云核场景知识包；若要"验证跨制品组合"选 IP。
7. **不做什么（确认）**：不建 KnowQL 类查询语言（依赖冻结+YAGNI，制品消费走现有结构化查询）；不建全量依赖图（54号§六.4 只做直接影响）；不让制品自动响应资料变化重编译（更新=新草稿）。
8. **MCP 网关范围**：制品发现在 MCP 侧走"get_knowledge 加 artifacts 视图"还是"Skills Extension 的 skills/list"？
   推荐：一期前者（不动三件套收敛决策、零协议风险），二期评估后者（需实测 fastmcp 3.4.7 对 2026-07-28 基协议与 extensions 的支持，若支持则一步拿到生态入口）。

## 九、结论

54号总纲给出的路线——"原始证据可回看、挖掘让它可找可读、知识制品让它可直接用于业务、真实反馈让它持续变好"——与 2026 年工业界（Nexus/Agent Skills/MCP/kg 服务）和学术界（Corpus2Skill/WiCER/Training-a-KB）的收敛方向一致，且治理要求（四种版本、来源链、专家校准、反馈只形成候选）严于公开水平。差距不在方向，在执行：**对象层与制作链均零代码、ADR 口径未调和、标准出口未接**。讨论已定六件事（§七 决策记录）：两型分类、LLM Wiki 最高优先、表格确定性代码构建、知识四形态模型、对象层=横切身份平面、kg 骨架吸收+域配置包。**实施走 §七末的五阶段路线**：架构定稿（P0 ADR + 两项遗留拍板 + 60号设计文档）→ 对象层落地 → wiki 管线最小闭环 → 表格抽取与通用表接入 → 制品生命周期与消费面收敛，以"第二个域零代码接入"为通用化终验。确认路线后进入 writing-plans 出分阶段实施计划。
