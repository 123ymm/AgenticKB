## 一、知识全面分类：四形态 + 三贯穿面

### 1.1 总览

| 层/面 | 一句话定义 | 已有覆盖 |
|---|---|---|

## 二、对象层与制品层为什么分开

### 2.1 原模型（10-14 用户四层描述）的混点：关联的持有者

原模型：L2 制品 = 一堆 wiki md（**md 之间自己带引用关系**）+ 结构化表（**命令类 md 和表互相关联**）；对象层在顶上做索引。

混点：**"关联"长在制品内部**——md 互链、md↔表关联，都是制品自己在持有关系。

定稿做的事只有一件：**把"关系的持有者"从制品搬到对象层**。

```
原来（原模型）：
  命令md"ADD POOL" ──正文引用──> 特性md"XX特性"
  命令md"ADD POOL" <──关联──> 命令数据表的某几行

现在（定稿）：
  对象[ADD POOL 命令] ──挂载──> 命令md（证据）
                    ──挂载──> 命令表的那几行（证据）
                    ──关系──> 对象[XX特性]
  md 之间的互链只是"关系是从哪抽出来的"依据
```

### 2.2 对象层=「把所有知识索引在一起的东西」：直觉保留 + 两处修正

用户核心直觉全部保留：统一关联枢纽、能连一个 md、能连表里某一行、所有知识经它关联。修正只有两处：

1. **位置**：不在最顶上。制品也引用对象（发布时固化对象 revision），证据/材料在对象下面被挂载——横切的一层平面，不是塔尖。
2. **内容**：不只是指针。对象上还存"有效值"——多条证据合成结果+人工修正后的值。理由：同一命令在 3 份 md 里描述有出入，对象只有指针的话每次查询都要自己合成一遍；合成规则放对象层一次合成处处可用，人工修正也才有地方放（否则重跑一次导入就把修正冲掉）。

### 2.3 不分开会断的三件事

1. **重编断链**：wiki 制品会重编、表格制品会重抽。关系长在制品里，制品一重编所有链接跟着漂或断。对象身份稳定，关系挂对象上才长期可靠。
2. **一个实体出现在多个制品**：ADD POOL 会同时出现在命令表制品、wiki 主题页、约束表里。对象长在制品里→同一命令三份身份。
3. **对象可无制品、制品可不经过对象**：13 万命令对象可以先建起来一张制品不发（云核现状）；长尾内容直接从证据组制品、不对象化（"可寻址≠是对象"）。两者生命周期不同：对象是活的（持续更新有效值），制品是发布物（草稿→试用→发布→停服，有版本快照）。

**一句话分工：对象回答"这个东西是什么、和什么有关系"；制品回答"做某件事需要哪些东西"。**

## 三、用户 / 知识库 / 知识对象 / 知识制品 四者关系

```
用户(user / mcp_key)
  │ 权限（库级：域RBAC+私有库+密钥域绑定，已有）
  ▼
知识库(kb) ── 权限边界，L0-L3 所有东西都住在库里
  ├─ 材料(L0)、证据(L1)     ← 不属于任何人，属于库
  ├─ 对象(L2)               ← 同上：公共资产，不属于任何用户
  └─ 制品(L3)               ← 有负责人(一个用户)、有状态机
```

| 关系 | 语义 |
|---|---|
| 用户 → 知识库 | 权限关系（读/管），已有体系 |
| 用户 → 对象 | **不拥有，只修正**：人工值挂对象上，带 who/when/reason 审计；谁改的能查，对象不因人而异 |
| 用户 → 制品 | 责任关系：负责人一个，发布/停服由他操作 |
| 制品 → 对象 | 引用关系：多对多，发布时固化 revision |
| 对象 → 证据/材料 | 挂载关系：一对多（md+表行同时挂一个对象） |

**制品归属与可见范围（2026-10-16 修订，原"一期跟库走"作废）**：制品**唯一归属一个 domain**（domain_id），内容可组装自多个知识库与上传文件；**与库权限完全独立、无嵌套无钳制**——策展开放是制品的核心价值（库里内容多，挑代表性内容做成制品开放给不该看整库的人）。安全机制不做硬钳制，改为**发布时知情提示**（provenance 聚合出私有库来源时提示创建者确认）。详见 61号 §5。

## 四、对象层设计：五张表

### 4.1 五张表总表

| 表 | 一句话 | 每行是什么 | 关键列 |
|---|---|---|---|
| `kb_types` | **类型的登记处**（对象的"模子"） | 一种类型（命令/特性/网元…） | type 编码、显示名、字段定义、身份规则、revision |
| `kb_objects` | **东西本身** | 一个知识对象（如 ADD POOL V1.0） | uuid（内部主键，永不改）、type+legacy_id+version（业务身份，唯一键）、logical（证据合成的字段值）、manual（人工修正值） |
| `kb_mounts` | **对象采用哪份证据** | 一次绑定（对象↔一个md/一行表数据/一个片段） | object_id、来源定位、status（active/detached/unverified）、manual 标志 |
| `kb_relations` | **对象间的边** | 一条有向关系 | from、to、relation_type、来源依据 source_key、置信、状态（待确认/已确认/已拒绝） |
| `kb_catalog` | **翻译层**（叫法归一） | 一条映射 | kind（version/mapping/alias）+ code + value |

### 4.2 两个必须说死的易误解点

1. **有效值不在任何表里存**。查询时 = logical（证据合成的值）∪ manual（人工值）运行时算出。这保证"来源值、人工值、有效值"永远分得开。
2. **关系表允许 to 为空**。md 里引用了还不存在的对象时，先存 target_id 原文（未解析引用），等该对象被导入后再解析挂上——引用悬空不丢、不报错。

### 4.3 kb_catalog 的目标态修正（2026-10-15 讨论）：别名并入对象身份解析

kg 现状：catalog 是独立目录表，只有 version/mapping/alias 三种 kind 且**不挂对象 uuid**——本质是"版本归一规则库"（海外 26.0.1 ↔ 国内 20.1.16，449 条），别名只是配角。

目标态：**任意对象都可有别名集合，别名是对象身份解析的输入**——导入时"同别名 → 命中同一对象"，不长出重复对象。版本映射保留在目录（归一规则，不是身份）。吸收时按此修正。

### 4.4 kb_mounts 的语义澄清（2026-10-15 讨论）

mounts **不是**"对象和哪些类型相关联"（那是关系表的事）。它回答：**这个对象的正文和字段值，从哪几份数据里来**。

来源端=四类"可定位载体"中的任何一类：

| 来源类型 | 例 | 挂载记录的内容 |
|---|---|---|
| 知识库原始文件 | 一份命令 md | 文件路径+快照哈希 |
| 文件内片段 | md 的某个章节/表格 | 文件+章节定位 |
| **结构化表的某一行** | AIMML 语法规则表的一行 | 表名+**业务主键** |
| **wiki 制品的 md** | wiki 页 | 同"原始文件"，但生产方是制品管线 |

**经讨论确认的两个机制**（用户直觉，与 kg 实测实现吻合）：

1. **表行挂载 → 查对象返回该行结构化数据**：挂载记录（表, 业务主键），查对象时顺挂载取回该行，行内列值参与合成对象"来源值"。三层值体验：查 ADD POOL 对象 → 返回**有效值 = 表行列值 ∪ md 描述 ∪ 人工修正**，每字段标着来自哪份挂载。
2. **对象↔证据/语料的关联不靠人工逐条做**：自动提议（导入解析/检索匹配），人工只审查修改。kg 已用状态机实现：程序产生的挂载状态为 **unverified（不贡献内容）**，人工核验后才 **active（贡献内容）**；人工解除变 detached，**同步永不复活**。人工逐条建挂载只在补漏时发生——22,938 个对象没有一个是手工挂的。

### 4.5 走例：一份 ADD POOL 的 md 导入，五张表各发生什么

```
0. 前提：kb_types 里已有 MMLCommand 类型
   （身份规则=命令名当 legacy_id + 必须有 version；字段=nf/参数明细/描述）
1. 导入方案读 md 的 YAML 头 → kb_objects 按 (MMLCommand, ADD_POOL, V1.0) 命中或新建一行
2. md 全文作为来源 → kb_mounts 插一行 status=active（这个对象采用了这份 md）
3. 正文里 [[XX特性]] → kb_relations 插一条候选：
   from=ADD_POOL对象, relation_type=引用, status=待确认, source_key=指向md里那段原文
4. YAML 头里版本号"RnX_1.2.3" → kb_catalog 查 version 映射，归一成国内版本"V1.0"
```

## 五、建模过程与对象/边的产生

### 5.1 "对象可以自己定义"——定义的是类型（模子），不是对象

页面定义新类型 = 填一张配置单（例：定义 WikiPage 类型）：

| 配置项 | 例 |
|---|---|
| 类型编码 + 显示名 | `WikiPage` / "Wiki页面" |
| 字段清单 | title（文本，必填）、tags（列表）、related（引用） |
| 身份规则 | frontmatter 的 id 当 legacy_id；**无 version**（wiki 页不分版本） |
| 归属约束 | 无父对象，可独立存在 |
| 来源配置 | 从 YAML 头的哪些键读哪些字段 |

定义后批量导入 wiki md 按模子建对象，**零代码**。kg 现状限制（吸收时改）：15 个类型写死在 `defaults.py`，页面只能改显示名不能新增类型——通用化改造第一条。

### 5.2 完整建模 = 两张配置单（边规则是 kg 缺口，吸收时补）

| 配置单 | 定义什么 | kg 现状 |
|---|---|---|
| 对象类型（kb_types） | 有哪些类型、字段、身份规则、归属约束 | 有，但 15 个类型写死在代码 |
| **边规则（待新增 kb_relation_rules）** | 哪些类型之间能连什么边、方向、基数（一或多）、是否依附、要不要证据 | **没有**——relation_type 是自由文本，页面随便加名称，零约束 |

最终形态：建模页面左边定义节点类型、右边定义边规则；实例和关系按规则批量进来时自动校验。交接文档将"通用类型、身份、依附与关系约束"列为高成本工作包。

### 5.3 对象和边的三条产生入口（批量导入是主通道）

| 入口 | 谁操作 | 产出 | kg 实测 |
|---|---|---|---|
| **① 批量导入（主通道）** | 用户配一次"导入方案"，跑批 | 对象+挂载成批进来 | 22,938 个对象 100% 这么来，没有一个手工建 |
| **② 管线抽取（边的批量来源）** | 程序解析 md 正文引用 | 候选关系（待确认状态，带证据和置信） | 45,401 条待确认关系全是这条线 |
| **③ 人工单个建/改（补丁）** | 用户在页面 | 补漏、拆分合并、裁决、改值 | 少量 |

**不是"每个对象用户定义"，也不是"每条边定制化代码"——用户定义的是方案（一张映射配置），对象和边按方案批量产生。** 导入方案配什么：

| 配 | 例（命令表→对象） |
|---|---|
| 来源 | 哪张表、什么范围 |
| 一行还是多行一个对象 | 按（网元+版本+命令名）分组，一组=一个对象 |
| 身份 | 命令名当 legacy_id，版本列当 version |
| 字段映射 | 列A→描述，列B→参数 |
| 关系映射 | 列C 是特性 ID → 建"属于特性"关系 |
| 材料挂载 | 整条记录、某字段、章节、表格行如何定位 |
| 同步边界 | 全量替换还是增量、重导/删除/冲突怎么处理 |

### 5.4 定制代码的位置：三层分工

```
格式读取器（会读 YAML头/正文/表格/双链）  ← 平台提供，通用
导入方案（哪读身份、哪读字段、怎么分组）  ← 用户配置，通用
领域适配器（云核的逻辑网元派生等特殊解析）← 配置包，隔离在核心外
```

换全新格式（如 JSON 头 wiki）才需要新读取器；普通新表、新 md 类型配置就够。

## 七、用户三层图与定稿模型对照（2026-10-15）

### 7.1 用户三层图原貌

```
语料层：知识库｜原始文档｜挖掘pipeline｜搜索pipeline（标准RAG）｜各类文档解析
知识制品：先两类——表格类（选1个或多个知识库→表名聚类→高频表→制品）；wiki类（前半key:value+后半任意内容+[[]]引用）
知识对象：即本体。定义对象类型、对象之间的边；实例化关联到不同知识制品的导入；
         对象层只做建模和输入适配，其余随下游变化；每个对象可看到关联的东西；
         制品内部关联/多制品间关联在转换成对象层时"继承"
```

### 7.2 逐行对照：一致项

| 用户表述 | 对应定稿模型 | 判定 |
|---|---|---|
| 语料层（知识库/文档/挖掘/检索/RAG/解析） | L0 材料 + L1 证据（三层图的"语料层"=两层合并称呼） | 一致 |
| 制品两型：表格类+wiki类 | 2026-10-13 拍板两型 | 一致 |
| wiki 形态：前半 key:value、后半任意内容、`[[]]`引用 | kg 交接 §5.2 WikiPage 样例逐字一致 | 一致 |
| 对象=本体，定义类型+边，实例化关联到制品导入 | kb_types+边规则（待补）+导入方案 | 一致 |
| 对象层只做建模和输入适配，其余随下游变化 | 读取器/导入方案/适配器三层分工 | 一致 |
| **制品内部关联、跨制品关联→转对象层时"继承"** | 59号 §6.7 修正3：互链=单向抽取管道，md 引用抽取成候选关系，人裁决后对象层持有 | **原话级一致** |
| 对象关联证据不靠人工，检索关联回去、人工只审查修改 | 机器提议人裁决 + 挂载 unverified→active 状态机 | 一致，且更具体 |
| 表格类跨库选表→表名聚类→高频表 | 表格制品发现机制（§6.3 新入册） | 一致（新补充） |

### 7.3 唯一差异：「制品在对象下一层」→ 两个方向都成立

用户图：制品在下、对象在上、本体"来源于"制品、Agent 基于对象**追溯**制品。

**来源方向成立**（用户直觉正确）；**交付方向是定稿补的另一半**：

```
方向①（来源方向，用户图）：
  语料 ──挖出──▶ 制品（表格/wiki）──挂载──▶ 对象
  对象的实例数据从制品导入，制品在对象"下面"      ✓

方向②（交付方向，定稿补充）：
  对象 ──被引用（发布时固化 revision）──▶ 制品 ──交付──▶ Agent
  制品是发布物（草稿→试用→发布→停服），Agent 直接查表格、读wiki ✓
```

同一张表格制品**双角色**：作为来源被对象挂载（它从语料抽出的行填充对象）+ 作为交付物引用对象（发布后行内容=对象在某 revision 的投影）。两个角色不矛盾——它们是两个方向。

若制品**严格只在对象下一层**，断三件事：①同一对象进多个制品→身份多份；②制品停服→对象悬空（对象生命周期必须独立于任何单个制品版本）；③长尾内容不对象化也可直接出制品（"可寻址≠是对象"）的路被堵死。

**定稿表述：对象层是中间的身份平面——向下挂载一切可定位载体（原始文件、片段、表行、制品md），向上被一切交付物引用（制品、检索）。**

### 7.4 四条关联全部成立，统一在 mounts 一张表

| 关联 | 走哪里 | 说明 |
|---|---|---|
| 对象 ↔ 原始语料 | mounts（来源=文件） | kg 现状就是 md 直挂，不强制经过制品 |
| 对象 ↔ 证据 | mounts（来源=片段/表行） | 用已有 014 定位协议填来源端 |
| 对象 ↔ 制品 | mounts（来源=制品md/表行） | 来源方向 |
| 制品 ↔ 语料 | 制品的 Evidence Link | ADR 铁律：制品必须回指原子来源，可回源 |

### 7.5 表格制品之间的关联：不做制品间外键，统一走对象层（2026-10-15 裁定）

理由四条：

1. 制品会重编重抽——制品间外键在重编时断链或错链（静默错链=五硬要求里唯一"生产事故级"断裂）。
2. 制品会停服——停一张表，挂着它的所有制品间外键悬空。
3. 同一实体跨制品需要**一份**身份，不是每对制品一套 join 规则；N 个制品两两映射是 N×(N-1)/2 套，对象层降到 N。
4. 表格制品可**跨知识库**选表——库间有权限边界，制品间物理外键越权。

**"像数据库那样关联"的正确落点**：外键声明放进导入方案的关系映射配置（"列X是特性ID→建立对象间的'属于特性'关系"），关联落地在对象层。技术对应：对象层=主数据/主键空间，制品=物化视图——视图之间不互相声明外键，靠底表主键关联。

### 7.6 合成图（用户三层图 × 定稿四形态）

```
语料层（用户叫法）= L0 材料 + L1 证据
  知识库｜原始文档｜挖掘管线｜检索管线（RAG 面）
        ▲ 挂载：自动提议（导入解析/检索匹配）→ 人工审查（unverified→active）
        │            来源端：原始文件 / 片段 / 表行 / 制品md
┌───────┴────────────────────────────────────────┐
│ 对象层（L2）＝ 用户的"知识对象"                      │
│   建模：类型(kb_types) + 边规则(kb_relation_rules)  │
│   身份：uuid + legacy_id + version + 别名集合       │
│   关系：制品内外互链抽取→候选→人裁决（用户的"继承"）    │
└───────▲────────────────────────────────────────┘
        │ 引用（发布时固化 revision）
┌───────┴────────────────────────────────────────┐
│ 制品层（L3）＝ 两型                                 │
│   表格类：跨库选表→表名聚类→高频表→制品（发现机制入册） │
│   wiki类：key:value头 + 正文 + [[]]互链            │
│   双角色：当来源（被对象挂载）/ 当交付物（引用对象）     │
└───────┬────────────────────────────────────────┘
        ▼ 交付面：MCP get_knowledge / st_结构化查询 / web
  Agent：读制品，或读对象，均可回溯到语料（ADR 铁律）
```

用户三层图作为四形态模型的**业务视角画法**收录（语料层=L0+L1 合并视图），两图一模型。
