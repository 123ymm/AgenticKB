# 知识制品与制作工作台：要开发哪些功能

> 面向产品讨论与功能验收。日期：2026-10-28。
> 这份文档只讲现在有什么、需要改成什么、用户怎样使用。数据库和开发约束保留在 [64号开发参考稿](64-知识制品管理与制品工作区-需求规格与现有实现对照-2026-10-28.md)。括号内编号用于和开发稿对应，可以跳过。
> 最新排期已收口：1.1.15 先统一知识制品区域，工作台／工作区放到 1.1.16。当前版本开发请阅读 [66号实施说明](66-知识制品统一界面-1.1.15开发需求说明书-2026-10-28.md)，本文保留完整目标说明。

## 一、这次主要要做什么

**保留已有的知识制品管理，新增一个能把资料加工成知识成果的制作工作台。**

两个入口各管一件事：

| 入口 | 用户在这里做什么 |
| --- | --- |
| **制作工作台** | 选资料、加工表格和文档、查看过程，做出准备交付的结果 |
| **知识制品** | 检查最终内容、人工微调、发布、管理版本和使用权限 |

完整过程是：

**打开工作区 → 接入资料 → 一步步加工 → 导出为制品草稿 → 在制品里检查 → 发布使用。**

工作区可以有很多半成品。用户选择要交付的结果，才把它送到知识制品中。**导出是送去检查，发布才是正式生效。**

## 二、当前已经有什么

表格类已经有基础版本：可以上传 Excel、管理列、编辑行和单元格、发布、回滚、管理成员，并供 Agent 查询。

Wiki 类已经在另一个分支中实现了一版：可以选知识库资料、生成目录和页面、人工编辑、发布、阅读、搜索及查看页面引用。

**这些主体功能继续用。本次主要增加制作工作台，以及它和制品草稿之间的连接。** Wiki 分支还需要整合和验收；原型里出现的按钮，不代表真实后端已经实现。

## 三、知识制品：保留哪些功能，需要补什么

知识制品内部继续保留 **设计态、运行态、成员、版本**。表格使用表格编辑器，Wiki 使用文档编辑器和阅读器。

| 功能模块 | 当前有什么 | 需要补充或修改什么 |
| --- | --- | --- |
| **制品列表与创建**（A01） | 已有制品列表和表格创建；Wiki 分支增加了类型选择 | 两类制品在同一入口管理；除了手工创建，也能接收工作台自动创建的草稿 |
| **设计态**（A02） | 表格能改字段和数据；Wiki 能改页面和正文 | 接收工作台做出的结果，继续检查和微调；补好人工修改保护，避免以后更新时丢失 |
| **运行态与发布**（A03） | 已有发布和正式内容查看 | 保持现有机制；草稿没确认发布前，不影响正在使用的内容 |
| **版本管理**（A04） | 已有发布历史和回滚 | 表格清楚展示数据变化，Wiki 清楚展示页面变化；回滚后仍能找到其他版本 |
| **责任人与权限**（A05） | 已有创建者、成员和使用权限管理 | 工作台导出时带上确认过的责任人；新制品默认不公开，不自动向 Agent 开放 |
| **人和 Agent 使用**（A06） | 已有表格查询，Wiki 分支有阅读和搜索 | 继续通过已有制品入口使用正式版；加工中的半成品不直接供业务 Agent 使用 |
| **Wiki 体验补齐**（A07） | 已有生成、编辑、阅读等基础能力 | 补齐目录展示、页面变化说明、使用说明，以及点击来源查看依据的体验 |

### 人工微调应该怎样使用

例如，“电源模块规格库”已经发布第 1 版：

1. 工程师进入设计态，修正一个功率值。
2. 修改先留在草稿里，其他人继续使用第 1 版。
3. 工程师检查后发布第 2 版，正式内容才更新。

如果只是修正一个值，直接在制品里改。如果整批抽取方法需要调整，再点击“返回构建工作区”。用户不用为了改一个单元格，重新走完整套制作流程。

## 四、制作工作台：主要新增哪些功能

### 1. 工作区管理（W01）

**当前：**还没有完整、独立的制品工作区管理。

**要开发：**创建、命名、打开、继续编辑和归档工作区，并设置负责人和协作成员。

一个工作区对应一项可以持续进行的整理任务。例如，同时保留“电源模块资料整理”“命令参数整理”“配置 Wiki 编纂”三个工作区。下次来了新资料，打开原工作区继续做，不必从头创建。

### 2. 接入不同资料（W02）

**当前：**表格主要接 Excel，Wiki 主要从知识库选材料；这些入口还没有整合到通用工作区。

**要开发：**让用户在一个工作区中选择不同来源：

- 上传 Excel。
- 选择知识库目录或文件。
- 选取知识库已经识别出的表格。
- 接入 SQL 表。
- 使用已有知识制品的正式内容。
- 从空白表开始，手工填写。

各来源可以分别形成自己的输入表。例如“产品资料表”和“库存表”各自保留，需要关联时再选择它们。不能要求所有资料先混进一张大表。

开发时先接通现有 Excel 和知识库资料，SQL 等新连接能力再单独建设。

### 3. 一步步加工资料（W04）

**当前：**已有一些导入、编辑和文档处理能力，但还不能在工作区里自由组合。

**要开发：**把常用处理方式做成可选择的加工动作，也就是“算子”。

| 用户想做的事 | 工作台应提供的功能 |
| --- | --- |
| 只保留需要的数据 | 筛选、选择列、删除列、调整字段名称 |
| 整理不同格式的表 | 统一字段、去重、合并、按名称或业务编号对齐 |
| 把文档结构变成表 | 拆出章节，再把指定章节展开成列 |
| 从正文获得字段 | 用 AI 提取型号、功率、分类等信息，加入新列 |
| 做特殊的数据转换 | 用自然语言提出要求，由 Agent 辅助生成脚本，试跑后保存使用 |
| 人工判断某个结果 | 直接修改，并保留修改记录和依据 |

每次加工后都能看见结果；不满意可以回看前面的结果，再尝试另一种处理。

### 4. 多张表一起加工，也能产生多张结果（W05）

**当前：**还没有完整的通用多表加工工作区。

**要开发：**每一步清楚显示用了哪些输入、产生哪些输出。

例如：

- 产品规格表 + 库存表 → 带库存的规格表。
- 产品文档 → 产品规格表、产品与设备配套表。

同一次整理可以得到两张不同的结果表，并分别送到两份知识制品。后续步骤可以选用其中一张，也可以引用更早的结果，不必永远使用紧邻的上一步。

### 5. 流程和内容两种查看方式（W03、W06）

**当前：**现有制品页面能看表格或 Wiki；制作过程的通用双视图需要新增。

**要开发：**

| 查看方式 | 适合做什么 |
| --- | --- |
| **流程画布** | 看资料从哪里来、经过哪些加工、哪里关联了多张表、最后产生什么 |
| **内容视图** | 给表格或文档足够空间，方便检查和修改 |

无论使用哪种视图，选中某个加工步骤后，都能在右侧修改它的设置，例如输入表、提示词和关联字段。

切换视图时，仍然看同一步、同一张结果。选中不同步骤，右侧设置和结果一起切换。完整表格或文章放在内容区域，不塞进画布上的小卡片里。

### 6. 先试跑，再正式执行，并能接着上次继续（W07）

**当前：**已有任务和模型调用基础，但还没有完整的工作区执行体验。

**要开发：**先用少量资料看效果，满意后再处理完整输入；保存结果和错误，支持重新打开、查看历史、取消和重试失败部分。

点击一个历史步骤，只看保存过的内容，不重新调用 AI。修改上游设置后，后面的旧结果要标明“需要更新”。新资料重复处理，记为一次新的执行，不把整套步骤再复制一遍。

### 7. 看清依据、问题和人工修改（W08、W10）

**当前：**已有部分来源记录、错误标记和权限检查，工作区中的统一查看与处理仍需建设。

**要开发：**知道某行数据或某页内容来自哪里；把抽取失败、空缺、重复、冲突和断开的引用显示出来，方便修正。

人工改过的内容要留下记录。以后更新资料时，不能悄悄改回机器生成值；新旧依据有冲突时，应让人核对。没有权限的原文，也不能通过工作区绕过去读取。

### 8. 用同一工作台制作 Wiki（W09）

**当前：**Wiki 分支已经有一条相对固定的生成流程。

**要修改：**保留已有生成能力，把取材、目录、写页、引用检查逐步接入工作区。以后可以配置要做哪些知识、每类从哪里取材、页面怎样写。

工作台遇到不同内容，使用不同展示：

- 表格：用数据网格查看和编辑。
- Wiki 页面：先选页面，再阅读或编辑正文。
- 页面之间的关系：看关系列表，或切换成知识关系图。

流程画布表示“怎么加工”；知识关系图表示“哪些知识互相关联”，两者分开。

## 五、工作台和知识制品之间，要开发哪些连接功能

| 功能 | 当前情况 | 开发后怎样使用 |
| --- | --- | --- |
| **选择结果并创建草稿**（X01、X02） | 还没有完整的工作区交付入口 | 选择结果，确认制品名称、责任人和内容，系统自动创建对应的表格或 Wiki 草稿 |
| **导出前检查**（X03） | 现有导入有部分校验，通用工作区交付还需新增 | 提前看数量、字段和问题；目标已有未处理草稿时提示处理，重复点击不会重复创建 |
| **以后更新同一份制品**（X04） | 不能可靠保证所有人工修改在重导后保留 | 原工作区处理新资料后，把结果送到已绑定制品的新草稿；保留人工修改并检查冲突，再由制品内发布 |

**首次导出后，制品还没有正式生效。** 用户应能点击“前往设计态”检查，再点击发布。以后更新也沿用同一个制品，不每次另建一个同名成品。

保护人工修改的功能没做好之前，先只开放首次创建草稿，不能为了快速接通流程而覆盖已有制品。

## 六、用一个完整例子判断是否做对

用户要制作“电源模块规格库”：

1. 创建“电源资料整理”工作区，选中知识库里的产品资料。
2. 选择加工动作，把需要的章节整理出来，再提取型号、功率等字段。
3. 接入库存表，按型号关联；通过表格检查匹配结果。
4. 在画布上看清输入和步骤，在内容视图里检查具体值。
5. 选中规格表，导出为“电源模块规格库”的草稿，确认责任人。
6. 到知识制品设计态里人工微调、填写说明，然后发布。
7. 同事和 Agent 使用正式版本。以后资料更新，再回原工作区处理，检查后发布下一版。

Wiki 的使用故事类似，只是中间结果和最终内容主要变成页面、目录和引用关系。

## 七、建议怎样安排开发

| 顺序 | 主要交付 |
| --- | --- |
| **先保住已有功能** | 表格制品继续正常使用；Wiki 分支单独整合验收，不阻塞表格工作台建设 |
| **接通表格制作** | 工作区、资料接入、基础算子、多表加工、流程／内容切换、结果保存 |
| **接通首次交付** | 工作台结果能自动创建制品草稿，并使用已有发布、版本和权限能力 |
| **补智能加工与持续维护** | AI 提取、失败重试、人工修改保护，再开放更新已有制品 |
| **扩展制作能力** | 把 Wiki 生成接入工作区；SQL、Agent 脚本等能力分别做好后启用 |

这份文档用于判断“功能是不是我们要的”。开发 Agent 使用 64 号的对应模块、实施补充和验收场景，不把这里的简要描述直接当成全部技术定义。
