# LLM 配置按域隔离——第一期实施设计

> 编号：62号
> 版本：V1.0
> 日期：2026-10-29
> 定位：`llm_service.yaml` 当前为全局单份配置、各 domain 共用；本设计实现**按域隔离**的第一期——chat（provider/models/密钥）与 rerank 按域覆盖，全局基底 + 域覆盖 deep-merge。embedding 锁全局（维度差异化后置二期）。
> 讨论过程：2026-10-29 可行性评估（分层结论：chat/rerank 容易、embedding 有 schema 硬约束、运行时旋钮不该拆）→ 第一期实施清单逐项落定。

---

## 一、背景与现状

### 1.1 配置流现状

- 真相源：`main_control_service/config/system/llm_service.yaml`，控制面以 `GET /api/v1/system/{name}/raw` 原样下发（`main_control_service/main.py:246`）。
- llm_service 启动时一次性拉取（`llm_service/config.py:209`），构建**单个** active chat provider + 单个 embedding/rerank provider（`llm_service/main.py:107-148`），无热加载，改配置需重启。
- `deploy-sync` 打包**永不触碰** `main_control_service/config/`（内外网配置差异所在，`deploy-sync.sh:16,158`）——域覆盖配置是服务器侧运维动作，不走进发布包。

### 1.2 已有的铺垫（本方案成本低的根因）

| 既有机制 | 位置 |
|---|---|
| 每请求携带 `knowledge_domain`：mining `llm_task_client` 与 serving `LlmClient`（ThreadLocal）均已带 | `knowledge_mining/mining/infra/llm_task_client.py:116`、`agent_serving_java/.../LlmClient.java:81,107` |
| 模板注册表**域覆盖优先、全局兜底**先例（`knowledge_domain = %s OR IS NULL` + 优先级排序） | `llm_service/runtime/template_registry.py:84` |
| chat 按请求选 model、per-model provider 懒构建缓存 | `llm_service/runtime/service.py:153-184` |
| 任务/调用记录表均有 knowledge_domain 列，用量对账面天然按域 | `agent_llm_*` 表 |
| 配置加载支持 `${ENV_VAR}` 密钥展开 | `llm_service/config.py:88-96` |
| deep-merge 帮助函数 | `llm_service/config.py:99` |

### 1.3 embedding 的硬约束（为什么锁全局）

- 检索表列写死 `embedding_vector_vec VECTOR(1024)`（`databases/asset_core/schemas/013_retrieval_assets_v2_staging.sql:110`），HNSW 迁移 `009` 强制校验维度、漂移即报错。
- 挖掘入库与检索查询必须同模型同维度，`QueryEmbedOperator` 已按 snapshot 维度 fail-fast。
- 结论：**第一期禁止任何域覆盖 embedding 字段**（校验强制，见 §四 A2）；维度差异化是独立的 schema+重嵌工程，另立二期。

## 二、范围裁定

### 2.1 做

- per-domain 的 `provider`（active_model、models、chat 密钥）与 `rerank`（base_url/api_key/model/timeout 等）。
- 配置形态：全局基底 + 域覆盖文件，控制面单点 merge，llm_service 拉成品。
- 热加载端点（internal-auth 双闸）。
- 域覆盖的保存校验、装载作废策略、配置状态可观测。

### 2.2 不做（显式排除）

| 不做 | 处理 |
|---|---|
| embedding 任何字段的域覆盖 | 保存时 400；绕过保存直接改文件则装载作废（§五 B2） |
| embedding 维度差异化 | 二期（动 schema/HNSW/重嵌，独立工程） |
| `worker/task/persist_writer/template/pool_max` 等运行时旋钮按域 | 服务级共享运行时，拆无意义；覆盖文件含这些键=校验拒绝 |
| 域管理员编辑权限 | 第一期站点管理员专属（同现有 system raw 权限档），域级授权后议 |
| 模型允许清单（allowed_models） | 后续可选增强 |
| kb-ui 域覆盖编辑界面 | 第一期服务器侧文件 + API；UI 二期 |
| 调用方（mining/serving）改动 | **零改动**——两侧早已每请求带 knowledge_domain |

### 2.3 兼容性铁律

**不存在任何域覆盖文件时，行为与现状逐字节一致**（单一配置路径原样走通）。此为回归红线。

## 三、设计总览

```
配置形态
  main_control_service/config/system/
    llm_service.yaml                    # 全局基底（现状，不动）
    llm_service.domains/                # 新增：域覆盖，只写差异
      odn.yaml                          #   例：只改 active_model / 自有模型+密钥 / rerank
      cloud_core_network.yaml

merge 语义（deep-merge，只在控制面做一次）
  effective(domain) = deep_merge(global, override(domain))
  - provider.models 按键覆盖同名条目，其余全局模型仍可用
  - active_model 域值优先
  - embedding 段强制 = 全局（校验）
  llm_service 启动拉 global + 域清单 + 逐域 effective 成品，自己不做 merge

请求流（调用方零改动）
  mining/serving → 带知识领域发起请求
    chat:  model 显式传 → 域生效模型集校验；model 为空 → 域 active_model 兜底
    rerank: model 为空 → 域 rerank.model 兜底
  llm_service → 按 (domain, model) 解析/缓存 provider → 落库 model_id 即实际路由
```

三条裁定（含理由，实施时不再重议）：

1. **merge 放控制面**：全局文件在控制面手里，只有它能让校验见到 merge 的另一半；llm_service 拿到的永远是成品，逻辑最薄。控制面不 import llm_service 代码（依赖方向），`_deep_merge` 抄一份到 `service.py`。
2. **坏覆盖作废回落全局，不拒绝启动**：一个域的配置错误不连坐其他域（服务不崩、该域回落共享配置、ERROR 日志 + 健康标记）。若后续有合规要求（域必须用自己的 key），可改为作废时该域 chat/rerank 直接报错——接口不变，改的是作废分支行为。
3. **显式 model 仍尊重调用方**：mining 部分阶段显式传 model（如 image_caption 的 `glm-4.5v`，`pipeline.py:427`）；显式值在**域生效模型集**（全局 ∪ 域覆盖后）里校验，通过即用。

## 六、llm_service 运行时按域解析

| # | 事项 | 落点 |
|---|---|---|
| C1 | `_get_chat_provider(model)` → `_get_chat_provider(model, domain)`：缓存键 `(domain or "__global__", model_key)`，provider 按该域 effective 配置构建；无覆盖域自动等价现状 | `runtime/service.py:153-184` |
| C2 | `submit()` 域默认模型：`model=None` 且域配置存在 → 域 `active_model`；显式 model → 域生效模型集校验（`resolve_model_config` 对未知 key 已 raise，`config.py:157`，只需传入域配置）。`_resolve_request_model` 加 domain 参数——落库的 `provider_name/model_id` 即实际路由，记录面不动 | `runtime/service.py:186-192, 397-422` |
| C3 | worker chat 执行：`_execute_chat` 补取任务 `knowledge_domain`（并入 `worker.py:160` 的 req 取数），传入 `execute_chat_attempt(model, domain)`；retry/重入队同理（模型已落库） | `runtime/worker.py:160-175`、`runtime/service.py:198-244` |
| C4 | rerank 同步端点：`ModelService` 持 per-domain rerank 默认模型与 provider（有覆盖的域建独立 `BigModelProvider`，embedding 半边填全局值——Phase 1 不应被用到）；`rerank()` 按 `body.knowledge_domain` 解析 | `runtime/model_service.py:104`、装配处 `main.py:131-148` |
| C5 | rerank 异步通道：`submit_rerank` 按域解析默认模型落库（对齐 `submit_embedding` 提交侧解析的既有约定，`service.py:462-467` 注释说明了理由）；`_execute_rerank` 按任务域选 provider | `runtime/service.py:487`、`worker.py:283-316` |
| C6 | 同步 `/execute`（`llm_call_mode: sync` 排障回退通道）同样带域解析——mining `llm_client.py:268` 传 model，域默认在服务端兜 | `api/tasks.py:99-119` |
| C7 | 调用方零改动（mining `llm_task_client.py:116`、serving `LlmClient.java` 已带 knowledge_domain） | 无 |

行为注记（实现时留意，不新增机制）：域 `active_model` 变更会改变幂等指纹的组成（request_params 含解析后 model_id）——跨配置变更的同 idempotency_key 重提会生成新任务而非复用旧结果，属期望行为（配置变了就该重跑）。

## 十一、验收标准

1. 域 A 配置自有 key+模型后：A 的 chat/rerank 走 A 的配置，域 B 与无覆盖域完全走全局，互不可见对方密钥。
2. 删除域 A 覆盖文件并 reload：A 立即回落全局，无重启。
3. 覆盖文件写坏（缺 api_key / 含 embedding）：保存时 400；绕过保存直接改文件则装载作废 + 告警 + 回落，服务不死。
4. 现有测试无回归；records 里各域 model 字段反映实际路由。
