## 全局背景（必先读）

CoreMasterKB 有**两条主线，彼此从不调 HTTP，只通过 PostgreSQL 交接**：

```
挖掘线 (Python) :8901                  检索线 (Java) :8081
  parse → segment → enrich               查询理解 → 路由 → 范围解析
  → 实体抽取 → 篇章关系                   → 多路召回 → 融合 → 重排
  → 检索单元 → 向量化 → 落库              → 上下文组装
  → build → publish release
       │                                          ▲
       └──── 写 asset_* 表 ──► PostgreSQL ──── 只读
```

- mining 是 `asset_*` 唯一写方；serving 对 `asset_*` 全只读。
- **发布语义**：挖完不立刻可检索，必须 build 快照 + publish release；serving 只认 active release。
- **域配置唯一真相源**：`main_control_service/config/`（4 域：cloud_core_network / generic / civil_engineering / odn），Java/Python 共读。
- 当前 git：单人直推 master，CI 只构建镜像不跑测试，无任何协作约定文件。

## 议题一：GitHub 协作模式

### 1.1 目标

> 用户原话：确保别人开发是 fork 我的分支向我提 PR，我自己开发是创建新分支再合并到主分支，总之确保主分支 OK。

即 **fork-and-PR（对外）+ feature-branch（对内）+ master 始终可发布**。当前是单人直推 master，要演进到这套流程。

### 1.2 现状（详见 [数据库现状 §6](./现状-数据库-database.md)）

- 远端 `github.com/fzl194/AgenticKB`（个人账号），仅 `master` 一个分支，仅 1 commit。
- CI（`.github/workflows/build.yml`）：push master / tag 触发，**只构建镜像推 GHCR**，零测试。
- ❌ 无 CODEOWNERS / CONTRIBUTING.md / PR 模板 / issue 模板 / LICENSE。

### 1.3 建议方案（分 4 步，按优先级）

#### 第 1 步：仓库设置（GitHub 网页面板，不在仓库里）

1. **Settings → General → Pull Requests**：启用 "Allow squash merge"（推荐，保持线性历史）、"Automatically delete head branches"（合并后自动删分支）。
2. **Settings → Branches → Add branch protection rule → `master`**：
   - ✅ Require a pull request before merging（要求 PR，即使你自己改也要走 PR）
   - ✅ Require approvals = 1（单人期可先关，有协作者后开；自己 PR 自己合并 GitHub 允许）
   - ✅ Require status checks to pass before merging（接第 3 步的 CI）
   - ✅ Require branches to be up to date before merging
   - ✅ Do not allow bypassing the above settings
   - 单人期最关键的一条是 **"Require a pull request before merging"**——它让你也不能直推 master，强制走 feature branch + PR，从机制上保证 master 始终经过 CI。
3. **fork 策略**：仓库已是 public（被 CI 推 GHCR 推断），别人能 fork。无需额外设置。若想限制 fork，组织仓库可关 "Allow forking"，个人仓库无法关。

> 你自己的工作流：`git checkout -b feat/xxx` → 改 → `git push -u origin feat/xxx` → GitHub 开 PR → CI 过 → squash merge → 自动删分支。对外：别人 fork → 改 → 向你提 PR → 你 review + CI 过 → merge。

#### 第 2 步：补协作约定文件（新建）

| 文件 | 作用 |
|---|---|
| `.github/CODEOWNERS` | 标注模块负责人，PR 自动申请 review（如 `knowledge_mining/ @you`）|
| `.github/PULL_REQUEST_TEMPLATE.md` | PR 描述模板（改了什么 / 怎么测 / 关联 issue）|
| `.github/ISSUE_TEMPLATE/bug.yml`、`feature.yml` | issue 模板 |
| `CONTRIBUTING.md` | 分支命名、提交格式（见 CLAUDE.md git-workflow：`<type>: <desc>`，type ∈ feat/fix/refactor/docs/test/chore/perf/ci）、PR 流程、本地测试命令 |
| `LICENSE` | 选一个（MIT/Apache-2.0），否则别人 fork 在法律上受限 |

#### 第 3 步：升级 CI（当前最大空洞——零测试）

现状 `build.yml` 只构建镜像。新增 `.github/workflows/test.yml`，PR 必跑：

```yaml
on: { pull_request: { branches: [master] } }
jobs:
  python-unit:
    runs-on: ubuntu-latest
    services: { pg: { image: postgres:16, env: {...}, ports: ['5432:5432'] } }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - run: pip install -e . && pip install jieba python-multipart  # 补 pyproject 缺的依赖
      - run: pytest llm_service/tests/ -q                            # 纯单测，最快
      # knowledge_mining 测试强绑真实 PG（CLAUDE.md 已警告），CI 里跑成本高，建议先只跑 llm_service
  java-unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
      - run: cd agent_serving_java && mvn -B test -o                 # L1 单测，排除 pg-integration,e2e
```

> ⚠️ knowledge_mining 测试的两个硬约束（`tests/conftest.py`）：autouse+session 级 `_ensure_schema` 连不上 PG 直接 error；默认不清表。CI 里跑要设 `KB_ALLOW_TEST_TRUNCATE=1` 并起独立 PG，**先放一放**，优先把 llm_service + java 单测接进 CI。

`build.yml` 改为仅在 push master / tag 时构建镜像（已是如此），PR 不构建镜像（省时间）。

#### 第 4 步：先收敛三处同构分裂（避免协作时踩坑）

新人上手最容易被这些坑带偏（CLAUDE.md 已记，详见挖掘现状 §5.2）：
- Python 依赖三份（`pyproject.toml` / `docker/Dockerfile` / `requirements.txt`）已漂移 → **以 `pyproject.toml` 为唯一源**，补 `jieba`/`python-multipart`，Dockerfile 改 `pip install -e .`。
- `.env` 解析三份（reset/export/import_db.py 各抄）→ 提取共用工具。
- 表顺序两份（`db_tables.py` vs `reset_db.py`）→ 统一。

### 1.4 议题一结论

最低限度三件事就能从「单人直推」演进到「受保护的主分支 + PR + CI 门禁」：**(a) master 开分支保护要求 PR；(b) 加 test.yml 跑 llm_service + java 单测；(c) 补 LICENSE + PR 模板 + CONTRIBUTING**。fork 对外天然支持，无需额外配置。

## 议题二：新增「知识库管理」模块

### 2.1 定位

用户原话：挖掘是一个「文档→切片→知识抽取」的 pipeline；要新建「知识库管理」模块，**前半部分（文档管理）用户关注，后半部分（知识抽取 pipeline）用户不关注**。

即把当前埋在 mining 里的「文档管理」能力**抽出来、做厚、做成用户可见的一等公民**，pipeline 作为它的下游消费者。

```
┌─────────────────────────────────┐    ┌──────────────────────────────────┐
│  知识库管理（新，用户关注）        │    │  挖掘 pipeline（已有，用户不关注） │
│                                 │    │                                  │
│  KB CRUD                        │───▶│  parse → segment → enrich → ...  │
│  文档 CRUD + 元信息 + 标签 + 分组  │ 触发│  → 实体抽取 → 检索单元 → 向量化     │
│  上传 / 重挖 / 软删除 / 回收站     │ run│  → build → publish release        │
│  状态可视化（草稿/处理中/已发布）   │    │                                  │
└─────────────────────────────────┘    └──────────────────────────────────┘
              │                                          │
              └── 写 kb_* / 文档元信息 ──► PostgreSQL ◀── pipeline 写 asset_*
```

### 2.2 现状交接点（详见 [数据库现状 §3](./现状-数据库-database.md) + [挖掘现状 §3](./现状-挖掘-knowledge_mining.md)）

当前**没有 KB 概念**，文档归属是隐式的三层：

1. **domain**（物理隔离边界，所有 asset_* 表都有 domain 列）
2. **source_batch**（一次 mining run 的输入集，`asset_source_batches`）
3. **channel**（发布通道，默认 prod）

文档从上传到可检索的 6 阶段状态机分散在 4 张表，**没有单一 `documents.status`**。上传（`POST /api/uploads`）只落盘不写库，与挖掘完全解耦。`upload_batch_id`（磁盘目录名）与 `asset_source_batches.id` 完全不对应（命名陷阱）。

当前 API 缺失（新模块的设计空间）：
- ❌ KB CRUD（`POST/GET /api/knowledge-bases`）
- ❌ 文档元信息编辑（`PATCH /api/documents/{id}`）
- ❌ 单文档重挖（`POST /api/documents/{id}/reparse`）
- ❌ 回收站（撤回立刻 publish，无 grace period）

### 2.3 数据模型选项（关键决策）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. domain 升格** | 新建 `knowledge_bases` 表，把 domain 升成实体（display_name/description/owner/visibility），`asset_documents.domain` 改成 `kb_id` | 概念最干净，1 domain = 1 KB | 大改：所有 asset_* 表的 domain 列要改，Java/Python 两侧都要动，迁移成本高 |
| **B. 加 kb_id 列**（推荐起步）| `asset_documents` 加 `kb_id` 列（保留 domain 做物理隔离），新建 `knowledge_bases` 表（id/domain/name/group/...）| 向后兼容，不动现有表结构，逐步迁移 | domain 与 kb_id 并存，短期内要理清「域隔离」vs「KB 分组」语义 |
| **C. 复用 source_batch** | 把 source_batch 当 KB | 零新表 | 语义错位（batch 是「一次摄取」，不是「一个 KB」），难表达「KB 内增删文档」|

> **建议起步用方案 B**：KB 是 domain 下的逻辑分组（一个域可有多个 KB，一个 KB 属于一个域），文档挂 kb_id。pipeline 仍按 domain 路由（无需改 pipeline），KB 只是文档集合的用户视图。

### 2.4 模块边界（建议）

新模块是一个独立的 Python 服务（或 mining 的一个新 router 组），**只做用户可见的文档/KB 管理**，不碰 pipeline 内部：

| 能力 | API 草图 | 现状是否已具备底层 |
|---|---|---|
| KB CRUD | `POST/GET/PATCH/DELETE /api/kb` | ❌ 全新 |
| 文档列表/详情/元信息 | `GET/PATCH /api/kb/{kb_id}/documents/{id}` | 🟡 已有只读 `/api/knowledge/documents`，缺 PATCH |
| 上传到 KB | `POST /api/kb/{kb_id}/uploads` | 🟡 现有 `/api/uploads` 落盘，要改成关联 kb_id |
| 触发挖掘（整个 KB 或单文档）| `POST /api/kb/{kb_id}/mine` / `/documents/{id}/reparse` | 🟡 现有 `POST /api/runs`，缺单文档重挖 |
| 软删除 + 回收站 | `DELETE /api/kb/{kb_id}/documents/{id}` + `POST .../restore` | 🟡 现有软撤回，缺 grace period / 回收站视图 |
| 状态可视化 | `GET /api/kb/{kb_id}/documents/{id}/status` | 🟡 状态分散 4 表，要聚合成单一 status 枚举 |

> 与 mining 的交接点保持单一：**新模块写 kb_* + 文档元信息 + 触发 run；pipeline 不变**。这样 pipeline 的 16~18 阶段、本体线、发布语义都不受影响。

### 2.5 议题二结论

新模块 = **把文档管理从 mining 里抽出来做厚**，pipeline 作为下游。建议数据模型用方案 B（加 `kb_id` + `knowledge_bases` 表，向后兼容），模块边界严格限定在「用户可见的 KB/文档管理」，与 pipeline 的交接点单一（触发 run）。最大设计风险是「状态聚合」——当前文档状态分散在 4 张表，新模块需要聚合成用户可理解的单一状态枚举（草稿 / 处理中 / 已发布 / 已撤回 / 回收站）。

## 议题三：本体未来形态——LLM-wiki

### 3.1 用户的判断

> 参考已有的本体部分 + llm_wiki，未来本体的构建很有可能是**大模型基于已有的所有相关知识进行 wiki 的编写 + 边链接的构建**。

「llm_wiki」仓库内不存在（已 grep 确认），是概念引用。最贴合的外部参照：

- **Stanford STORM**（[arXiv 2402.14207](https://arxiv.org/abs/2402.14207)，273 引用，[开源](https://github.com/stanford-oval/storm)）：**S**ynthesis of **T**opic **O**utlines through **R**etrieval and **M**ulti-perspective question asking——LLM 先多视角提问 + 检索研究，再生成带目录、章节、内联引用的 Wikipedia 式长文。
- **Ontology-grounded KG construction**（[arXiv 2412.20942](https://arxiv.org/html/2412.20942v1)）：用本体作 schema 约束 LLM 抽取，比 schema-free 抽取更一致。
- **Entity linking to Wikidata/Wikipedia**：抽取后做消歧接地（与现有 `ontology_alias_dictionary` 同思路）。

映射到 CoreMasterKB：**STORM 式「研究→大纲→带引用长文」≈ 用户说的「基于所有相关知识写 wiki」**；**本体作 schema 约束 + 边链接 ≈ 用户说的「边链接构建」**。

### 3.2 现状（详见 [本体现状文档](./现状-本体-ontology.md)）

**架构层面意外地贴合 wiki 范式**，已有：
- ✅ 版本治理 + active 唯一约束（`ontology_versions`）——天然支持「生成 draft → 人审 → publish」
- ✅ **出处强约束**（`ontology_evidence_nodes` + DB CHECK）——每个实体/关系必带原文出处，wiki 的「引用」已就位
- ✅ 草稿编辑器 + 候选评审 API（`/ontology/draft`、`/ontology/candidates/{id}/review`、`/ontology/promote`）——wiki 编辑的后端骨架
- ✅ **双通道逃生口**（`__untyped__` mention → 人审 → 归纳升类型）——「边写边发现新条目」机制
- ✅ entity_graph 检索算子（递归 CTE + confidence 衰减 + 回证据段）——本体写好立刻可被检索消费，闭环已通

**但两个关键自动化缺失**：
- ❌ **类型归纳 no-op**：`mining-ontology-induction` 模板真无 fallback，本体类型永不自动扩展（订正：CLAUDE.md 说 entity_extract 也 no-op，不准确——它有 compat 兜底在 3 个非 generic pack 下正常工作）
- ❌ **跨文档全量聚合 + 边写边链机制不存在**：当前归纳输入是「已确认的 `__untyped__` 实体」，范围太窄；LLM 写 wiki 条目时主动给 canonical 实体建链的算子完全没有
- ❌ **wiki 条目载体表缺失**：`ontology_entities.definition` 只是一句话，没有「长文章 + 章节 + 引用列表」结构
- ⚠️ **`/api/v1/search` 的 entity_graph 在特定路由配置下恒空**（虚拟线程不继承 ThreadLocal，DomainContext 漏设）——阻塞「生成的本体能在主入口验证」

### 3.3 演进路线（建议分 4 阶段）

#### Phase 1：让自动归纳先跑起来（最小闭环，1~2 周）
- 补 `mining-ontology-induction` prompt + JSON Schema（建议输入：「已知类型 + 一批文档级实体清单 + 各实体的原文摘录」，输出：「type_name/definition/examples/members」）
- 4 个 scenario pack 的 `domain.yaml` 注册该模板
- 修 `/api/v1/search` 的 DomainContext 虚拟线程 bug（SearchService 两个 runAsync lambda 包 `wrapRunnable`）
- **产出**：本体类型能自动提议 → Gate1 真正有人审内容；entity_graph 在内置主入口可用

#### Phase 2：跨文档聚合 + wiki 条目载体（3~4 周）
- 新建 `ontology_wiki_articles` 表（id / domain / entity_id / title / content_md / section_json / citation_list_json / status / version）——长文 + 章节 + 引用列表
- 新增全局阶段 `wiki_compose`：输入「全部文档 + 已有本体 + STORM 式多视角提问」，输出「每个核心实体的 wiki 条目草稿」
- 复用现有 `ontology_evidence_nodes` 作引用来源（出处强约束已就位）

#### Phase 3：边写边链（4~6 周）
- 新增算子 `wiki_link`：LLM 写 wiki 条目时，对当前 canonical 实体集合做 entity linking，自动产出 `ontology_entity_relations` 候选（带 NPMI 质量闸）
- 这是用户设想的核心——当前最近似的 `entity_relations` 是单段两两 pattern 匹配，做不了「基于整篇 wiki 内容的全局建链」
- 草稿状态写入 `ontology_candidates`，走现有 Gate1 人审

#### Phase 4：软评审工作流（持续）
- 当前两道 Gate 是阻塞式暂停（`pause_for_review`），LLM-wiki 风格更接近「持续生成 → 评审队列 → 增量发布」
- 把 Gate 从硬阻塞改成事件流：本体持续生成 candidate，评审队列异步消费，promote 时增量发版（现有 `promote_accepted_candidates` 已具备克隆+追加语义）

### 3.4 议题三结论

**架构是好的起点**（版本治理、出处强约束、双通道逃生口、人审 API、草稿编辑器、检索闭环），离「LLM 基于全部知识写 wiki + 自动建链」约 60% 工作量，集中在 4 块：**prompt 工程 + 跨文档全局阶段 + wiki 载体表 + 边写边链算子 + 软评审工作流**。建议按 Phase 1→4 演进，Phase 1（补归纳模板 + 修 ThreadLocal bug）是性价比最高的第一步，能让现有「半运转」系统先变「全运转」。

## 议题四：挖掘 / 检索现状总览

> 详细三色清单见各现状文档。这里只给高层判断。

### 4.1 挖掘（knowledge_mining）

- 🟢 **稳健**：parse / segment / enrich / discourse / retrieval_units / embedding / db_write / publish / withdrawal；document lifecycle 的 NEW/SKIP/RESTORE/UPDATE 幂等；三层文档模型（document 身份 / snapshot 内容寻址 / link 事件流）设计精巧。
- 🟡 **降级**：resolve / entity_relations 依赖本体线；contextualizer 在 cloud_core_network 被 policy 关；per-domain 分库代码已通但 registry 把 4 域指同一物理库。
- 🔴 **静默失效**：**`ontology_induction` 模板未注册 → 本体类型永不自动归纳**（核心）；`generic` pack 无 `llm_templates` 全量降级；`eval.py` 死代码（引用 SQLite API）；依赖/`.env`解析/表顺序三处同构分裂。

### 4.2 检索（agent_serving_java）

- 🟢 **稳健**：`/api/v1/search` 主流程；LLM-first QU + 规则兜底；三级 FTS 降级（tsvector→trigram→LIKE）；cascading rerank；ContextAssembler 去重+矛盾检测+3000t 压缩；域路由（懒建池+建池即验连）；**算子/范式系统设计完整（19 算子 + 7 项编译校验 + 拓扑执行），范式路径无 ThreadLocal bug**。
- 🟡 **已知 bug**：**语义缓存污染**（降级/空结果写入 cache，`evict` 零调用）；**entity_graph 在 `/api/v1/search` 特定路由配置下恒空**（DomainContext 漏设，范式路径不受影响）；selectWithMeta 行放大（依赖消费者去重）；multi_query 算子孤立无下游。
- 🔴 **死代码**：`RetrievalRouter.BUILTIN_ROUTES`（intent→routes 定义后从未读取，pipeline-03 文档据此写过时描述）；`ScenarioPackReader` 旧实现；`docs/pipeline-0X-*.md` + `code_guide.md` 过时（部分描述已删除的 v4 `agent_serving_zdy`）。

### 4.3 三条最该先修的（跨模块）

1. **`mining-ontology-induction` 模板**（议题三 Phase 1）——打通本体自动归纳，让本体线从「半运转」变「全运转」。
2. **`/api/v1/search` 的 DomainContext 虚拟线程 bug**——SearchService line 294/323 的两个 runAsync 包 `wrapRunnable`，让 entity_graph 在内置主入口可用。
3. **语义缓存污染**——`SemanticCacheService.store` 加「无 seed item 不写」guard + 把 `evict(domain)` 接到 release 发布钩子。

### 4.4 议题四结论

挖掘和检索**主线都跑通且稳健**，问题集中在：本体线的自动归纳断裂、检索主入口的若干已知 bug（多数已有范式路径绕过）、以及大量过时文档/死代码/同构分裂。这些不影响「跑起来」，但严重影响「协作上手」和「演进」——议题一、二、三的推进都会撞到它们，建议作为前置清理。
