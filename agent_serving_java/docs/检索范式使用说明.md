# 检索范式（可插拔检索算子系统）使用说明

> 适用对象：用画布搭建/调试检索范式的人，以及通过接口调用范式做评测的测试系统。
> 入口：前端 kb-ui 左侧导航「**检索范式**」。
> 后端服务：`agent_serving_java`（`/api/v1/operator/*`、`/api/v1/paradigm/*`），与现有 `/api/v1/search` 并存、互不影响。

---

## 1. 这是什么

把检索流程拆成一个个**算子**（query_embed、dense_vector、fts、rrf、model_rerank、assemble…），在画布上**拖拽 + 连线 + 配参数**组成一张有向无环图（DAG），就是一个**范式**。范式可以：

- **试运行**：当场跑当前画布看效果；
- **发布**：固化成**不可变版本**，得到稳定的 `范式ID + 版本号`；
- **被测试系统调用**：`POST /api/v1/paradigm/{id}/search` 拿检索结果算指标（召回/精确/MRR/NDCG…）。

用途：测不同检索范式的增益（纯向量 vs 向量+重排 vs 多路融合…）、调参对比、为生产链产出喂给 LLM 的上下文。

---

## 2. 核心概念

| 概念 | 含义 |
|---|---|
| **算子 (Operator)** | 检索流程的最小可插拔单元，有类型化输入/输出端口（slot）和可调参数 |
| **slot** | 算子的输入/输出端口，有类型（向量/范围/候选/查询理解/上下文包…） |
| **范式 (Paradigm)** | 一张完整的检索 DAG（算子 + 连线 + 参数 + 终点） |
| **版本 (Version)** | 范式某次发布的**不可变快照**；同一 `ID+版本` 调用结果可复现 |
| **终点算子** | DAG 的出口：`collect`（候选列表，测试用）或 `assemble`（ContextPack，喂 LLM） |
| **检索范围 (textKind)** | dense_vector 的参数：在 raw_text / 生成问题 / 两者 中检索 |

---

## 3. 快速上手（1 分钟跑出结果）

1. 顶部/侧边确认**领域**为 `cloud_core_network`（当前库语料是 application-assurance 的 `aa-*` 命令，查询词用 `aa-interface` 这类才有结果）。
2. 「检索范式」→ **新建范式** → 填名称 → **模板**选 `① 纯向量检索（基线）` → **创建并编辑**。
3. 画布已自动连好 4 个算子。右侧「运行」框输入 `aa-interface` → **试运行草稿** → 下方出现候选列表 + 执行链路。
4. 想对比检索范围：点画布上的 **向量检索** 节点 → 右侧把「检索范围」改成 `question` → 再试运行（候选会整批变化）。
5. 满意后：**校验** → **发布**（得到 v1）。右侧「接口调用」区出现端点和「复制 curl」。

---

## 4. 画布操作

- **加算子**：从左侧面板把算子**拖**到画布。
- **连线**：从一个节点**右侧输出口**拖到下游**左侧输入口**。
- **选中**：点节点 → 蓝色高亮环，右侧显示「节点参数」。
- **配参数**：右侧面板按算子 schema 自动渲染（下拉/数字/开关/标签/权重）。
- **设输出终点**：右侧「输出（终点算子）」下拉，选 `collect → candidates` 或 `assemble → contextPack`（被选节点显示绿色环）。
- **删除节点/连线**：选中后按 `Delete`；节点也可在右侧「删除节点」。
- **连线帮助**：画布右上角「？连线帮助」查看规则。

---

## 5. 连线规则

1. **方向**：右侧输出口 → 下游左侧输入口（输出↔输出、输入↔输入连不了）。
2. **类型一致**：同类型才能连（向量→向量、范围→范围、候选→候选…）。唯一例外：**候选 → 融合算子的多入口**。类型不符**连不上**并弹中文提示。
3. **单入 / 多入**：普通输入口只接一条（再连会替换旧线）；融合算子的 `candidates` 可接多条。
4. **不能成环**：整图必须是 DAG。
5. **入口**：`query` 输入口可**不连**（运行时自动用请求的查询）；**检索算子的 `scope` 必须连 `scope_resolve`**，否则校验报 `missing_required_input`。
6. **终点**：必须选一个终点节点的输出 slot 作为范式结果。

## 6. 算子目录（共 18 个）

| 类别 | 算子 | 输入 → 输出 | 关键参数 |
|---|---|---|---|
| **入口** | `request_input` | (无) → query(文本) | — |
| **查询变换** | `query_embed` | query → queryEmbedding(向量) | — |
| | `hyde` | query → queryEmbedding(向量) | — (先用 LLM 生成假设文档再嵌入) |
| | `query_understanding` | query → understanding(查询理解) | useLlm(建议性) |
| | `multi_query` | query → variants(字符串列表) | maxVariants ⚠️暂无下游消费者 |
| **范围** | `scope_resolve` | (无) → scope(范围) | — |
| **检索** | `dense_vector` | queryEmbedding, scope → candidates | **textKind**(raw_text/question/both), topK |
| | `fts` | query, scope → candidates | topK（三级降级 tsvector→trigram→LIKE） |
| | `entity_exact` | understanding, scope → candidates | topK（实体名精确匹配） |
| | `graph_expand` | seeds(候选), scope → candidates | maxDepth, maxResults, relationTypes |
| **融合** | `rrf` | candidates(多入) → candidates | k |
| | `weighted_rrf` | candidates(多入) → candidates | k, weights(**按 source 名**) |
| | `identity` | candidates → candidates | — (直通) |
| **重排** | `model_rerank` | candidates, query → candidates | topK, threshold（跨编码器模型） |
| | `llm_rerank` | candidates, query → candidates | topK（LLM 列表式） |
| | `score_rerank` | candidates → candidates | threshold（按分数兜底） |
| **输出** | `collect` | candidates → candidates(终点) | maxItems |
| | `assemble` | candidates, understanding, scope → contextPack(终点) | maxItems, maxExpanded, relationExpansion |

说明：
- **向量化可替换**：用 `query_embed` 的地方都能换成 `hyde`（输出都是 queryEmbedding）。
- **weighted_rrf 的 weights 按 source 名**（如 `dense_vector`、`lexical_bm25`）键控，不是按节点 id。
- **graph_expand** 产出的是段落级候选（适合补充上下文/collect），与 unit 级候选混融需注意语义。

### 6.1 三种重排算子的区别（model_rerank / llm_rerank / score_rerank）

三者都把候选**重新排序**，区别在"用什么排、调不调外部服务、成本质量"：

| 算子 | 用什么排 | 调外部？ | 成本/延迟 | 失败行为 |
|---|---|---|---|---|
| **模型重排** `model_rerank` | 专用**重排模型**（交叉编码器，如 BigModel rerank） | 调 llm_service `/models/rerank` | 中 | 模型不可用→回落输入顺序 |
| **LLM 重排** `llm_rerank` | 通用 **LLM** 做列表式排序 | 调 LLM（一次推理） | **高** | LLM 失败→回落输入顺序 |
| **分数兜底** `score_rerank` | **已有分数**（余弦/融合分）直接降序 | **不调**，纯本地 | **零/最快** | **永不失败** |

- **打分方式**：模型重排对每个 (查询, 候选) 对单独算相关性分（专用交叉编码器，质量高性价比好）；LLM 重排把 top-N 一起喂给 LLM 做**列表式**排序（考虑候选间相对关系，更懂复杂语义但慢且贵）；分数兜底不重新判断，直接用上游已有分数排序。
- **输入**：模型/LLM 重排需要 `候选 + query`；分数兜底只需 `候选`。
- **参数**：model_rerank = topK + threshold；llm_rerank = topK；score_rerank = threshold。
- **怎么选**：生产默认 `model_rerank`（最平衡）；复杂查询/候选少/不在乎慢贵可试 `llm_rerank`；不想花钱或没重排服务用 `score_rerank`；想测增益就分别接三个发三版做对比。
- **与原 pipeline 的关系**：原固定 `/api/v1/search` 里三者是级联（model→llm→score，前一级成功跳过后续，score 兜底）；算子系统里它们是**独立算子**，按需选用，也可完全不重排。

### 6.2 四个查询变换算子的区别（query_embed / hyde / query_understanding / multi_query）

这 4 个**输出类型不同、用途不同、喂给谁不同**，不是同类替换（只有 query_embed 和 hyde 可互换）：

| 算子 | 做什么 | 输出 → 喂给谁 | 调外部/成本 |
|---|---|---|---|
| **查询向量化** `query_embed` | 把查询原文直接嵌入成向量 | queryEmbedding(向量) → `dense_vector` | 1 次嵌入 |
| **HyDE** `hyde` | 先用 LLM 生成"假设性答案文档"再嵌入 | queryEmbedding(向量) → `dense_vector` | LLM + 嵌入（最贵） |
| **查询理解** `query_understanding` | 抽取意图/实体/关键词/范围/子查询 | understanding(查询理解) → `entity_exact`、`assemble` | LLM 优先，失败回落规则 |
| **多查询扩展** `multi_query` | 生成查询的多个语义变体（同义改写） | variants(字符串列表) → ⚠️暂无下游 | 调 LLM，失败回落原查询 |

- **输出类型决定接谁**（最关键）：向量类（query_embed/hyde）只能接 `dense_vector`；查询理解类只能接 `entity_exact`/`assemble`；`multi_query` 输出字符串列表，当前算子集**无算子消费**（变体扇出成并行多路检索是后续特性，先别用作主链）。
- **query_embed vs hyde（可互换）**：两者输出都是 `queryEmbedding`。query_embed 嵌入**裸查询**；hyde 嵌入 LLM 编的**假设答案**——假设答案在向量空间更接近真实答案文档，对短/模糊查询语义召回更好，但多一次 LLM 调用、更慢更贵。
- **query_understanding 是"理解"不是"检索"**：不产候选，产结构化理解（意图 7 类、实体、关键词、范围、子查询）；`entity_exact` 靠它取实体名、`assemble` 靠它做证据分类；LLM 优先抽取，失败自动回落规则（jieba+正则）零成本兜底。
- **怎么用**：向量链放 query_embed（默认）或 hyde（要 HyDE 增益）二选一；要用 entity_exact/assemble 必须放 query_understanding；multi_query 暂别接。

### 6.3 范围解析算子的作用（scope_resolve）

**作用**：根据请求的 `domain` + `channel`，解析出"**这次检索要在哪批文档里做**"——即当前生效版本的文档范围。

- **无输入**（从请求的 domain/channel 读，不连上游）；**输出** `scope`(范围)，含：
  - `releaseId` / `buildId`：当前**生效的发布版本**；
  - `snapshotIds`：该版本包含的**文档快照 id 列表**（检索的实际范围）。
- **为什么必需**：知识库是版本化的（挖掘产 build → 发布 release；某 release 对 domain+channel 为 active）。检索只能在当前生效版本的快照里做——所有检索算子的 SQL 都按 `document_snapshot_id IN (snapshotIds)` 过滤。**因此 `dense_vector` / `fts` / `entity_exact` / `graph_expand` / `assemble` 的 scope 口都必须连 scope_resolve**（否则校验报 `missing_required_input`）。几乎每个范式都要放一个。
- **失败行为**（FAIL_FAST）：该 domain+channel 无生效版本→`no_active_release`(503)；有多个→`multiple_active_releases`(409)。
- **⚠️ 别和 textKind 混淆**：scope_resolve 的 scope 解决"在**哪个版本/哪批文档快照**里检索"（文档维度）；dense_vector 的 textKind 解决"在这批文档里检索**哪种单元**（原文/生成问题）"（单元维度）。

### 6.4 组装上下文算子的使用（assemble，生产用）

`assemble` 是**生产用的终点算子**：把排好序的候选组装成结构化的 **ContextPack**（喂 LLM/前端，与现有 `/api/v1/search` 同结构）。与 `collect`（只吐候选列表，测试用）相对。

**产出**（ContextPack）：`items`（种子 + 回溯原文段落 + 图扩展支撑段落，带文本/证据角色/引用）、`relations`（条目关系边）、`sources`（来源文档）、`evidence_groups`（按快照分组）、`issues`/`suggestions`（无结果/低置信/矛盾检测 + 建议）。内部复用 `ContextAssembler`：种子→回溯原文→沿 RST 关系图扩展→证据角色分类→上下文压缩(约 3000 token)→分组。

**怎么用（关键：3 个输入都要连）**——assemble 是终点且有 3 个必填输入：

| 输入口 | 连谁 | 为什么 |
|---|---|---|
| `candidates` | 重排/融合/检索的输出 | 排好序的候选 |
| `understanding` | **`query_understanding`** | 证据角色分类、查询上下文 |
| `scope` | **`scope_resolve`** | 回溯原文段落、图扩展都要在范围内 |

最小链：`query_understanding + query_embed + scope_resolve + dense_vector + assemble`。连线后右侧「输出」选 `assemble → contextPack`，试运行结果面板显示 ContextPack（而非候选表）。**最省事：新建时选模板 ④ 生产链 或 ⑪ 三路全融合 + 生产链，已连好。**

**参数**：`maxItems`（最终条目数，默认 10）、`maxExpanded`（图扩展上限，默认 20）、`relationExpansion`（是否沿关系图扩展，默认 true）。

**何时用**：测试/评测用 `collect`（候选列表，方便算指标）；生产/喂 LLM 用 `assemble`（结构化 ContextPack）。

### 6.5 四个检索算子的区别（dense_vector / fts / entity_exact / graph_expand）

都产候选，但**召回方式、输入、适用场景**不同：

| 算子 | 召回方式 | 输入 | 适用 |
|---|---|---|---|
| **向量检索** `dense_vector` | pgvector 余弦**语义近邻**，按 textKind 过滤单元 | queryEmbedding + scope | 概念/语义查询、模糊表达 |
| **全文检索** `fts` | PostgreSQL **词法匹配**，三级降级 tsvector→trigram→LIKE，jieba 分词 | query + scope | 精确关键词、命令名、英文/数字 |
| **实体检索** `entity_exact` | 对 entity_refs **JSONB 精确匹配**实体名，固定高分 0.95 | understanding + scope | 命令名/网元名精确查找 |
| **图扩展** `graph_expand` | 从**种子候选**沿段落关系图 BFS 扩展邻居（不独立起头） | seeds(候选) + scope | 给已有结果补充上下文邻居 |

- **关键差异**：前三个是"从零召回"，`graph_expand` 是"从已有候选扩展"——它需要 `seeds`（上游某检索器的候选），不能作为第一步检索。
- **输入不同**：dense 要向量（query_embed/hyde）；fts 要查询文本（自动绑定）；entity_exact 要查询理解（query_understanding）；graph_expand 要种子候选。
- **都需要 scope**（连 scope_resolve）。
- **怎么用**：语义查询用 dense；精确命令/关键词用 fts；命令名精确用 entity_exact；想多路互补就并联几个 → 融合；想补上下文就在某检索器后接 graph_expand。

### 6.6 三个融合算子的区别（rrf / weighted_rrf / identity）

把**多路**候选合并成一路：

| 算子 | 做什么 | 参数 |
|---|---|---|
| **RRF 融合** `rrf` | 倒数排名融合，多路按 `Σ 1/(k+rank)` 求和，各路**等权** | k |
| **加权 RRF** `weighted_rrf` | `Σ weight_source/(k+rank)`，各路**可调权重** | k、weights |
| **直通** `identity` | 单路原样透传（**不融合**） | — |

- **怎么选**：多路检索后用 `rrf`（等权）或 `weighted_rrf`（想让某路更重，如向量 1.2 / 词法 1.0）；单路检索可不接融合，或用 `identity` 占位保持范式形状统一。
- **输入是"多入口"**：rrf/weighted_rrf 的 `candidates` 可接多条线（dense、fts、entity 都连进来）。
- **⚠️ weights 按 source 名键控**（如 `dense_vector`、`lexical_bm25`），不是节点 id；两个同类型节点的候选 source 相同，会被当成一组、共用一个权重。

### 6.7 其余算子（collect / request_input / multi_query）

- **`collect`（收集候选，测试用终点）**：把候选原样吐成列表（id/score/source/metadata），按 `maxItems` 截断。与 `assemble`（产 ContextPack）相对——测试/评测用 collect，方便算指标。
- **`request_input`（查询入口）**：把请求的 query 作为输出 slot，供显式连线（`request_input.query → query_embed.query`）。也可**不用**——起点算子的 query 口不连时会自动绑定请求查询；它只是让入口在画布上显式可见。
- **`multi_query`（多查询扩展）**：用 LLM 生成查询的多个语义变体，输出字符串列表。⚠️ **当前算子集没有消费它的算子**（把变体扇出成并行多路检索是引擎后续特性），所以现在能放但接不到下游，先别用作主链。

### 6.8 参数速查（每个算子可配置的参数）

**无参数**（5 个）：`request_input`、`query_embed`、`hyde`、`scope_resolve`、`identity`。

**有参数**：

| 算子 | 参数 | 类型 | 范围/取值 | 默认 | 含义 |
|---|---|---|---|---|---|
| query_understanding | `useLlm` | 布尔 | true/false | true | 用 LLM 理解（建议性，引擎自动决定） |
| multi_query | `maxVariants` | 整数 | 0–10 | 2 | 额外变体数 |
| dense_vector | `textKind` | 枚举 | raw_text / question / both | raw_text | 检索范围（原文/生成问题/两者） |
| | `topK` | 整数 | 1–200 | 20 | 返回数量 |
| fts | `topK` | 整数 | 1–200 | 20 | 返回数量 |
| entity_exact | `topK` | 整数 | 1–200 | 20 | 返回数量 |
| graph_expand | `maxDepth` | 整数 | 1–5 | 2 | BFS 扩展深度 |
| | `maxResults` | 整数 | 1–50 | 10 | 最大扩展数 |
| | `relationTypes` | 字符串数组 | 关系类型列表 | 空=全部 | 限定沿哪些关系扩展 |
| rrf | `k` | 整数 | 1–1000 | 60 | RRF 常数 k |
| weighted_rrf | `k` | 整数 | 1–1000 | 60 | RRF 常数 k |
| | `weights` | 对象 | {source名: 数值} | 空 | 各路权重（**按 source 名**，如 dense_vector:1.2） |
| model_rerank | `topK` | 整数 | 1–200 | 10 | 返回数量 |
| | `threshold` | 小数 | 0–1 | 0 | 分数阈值（过滤低分） |
| llm_rerank | `topK` | 整数 | 1–200 | 10 | 返回数量 |
| score_rerank | `threshold` | 小数 | 0–1 | 0 | 分数阈值 |
| collect | `maxItems` | 整数 | 1–500 | 20 | 最大返回数 |
| assemble | `maxItems` | 整数 | 1–50 | 10 | 最终条目数 |
| | `maxExpanded` | 整数 | 0–50 | 20 | 最大图扩展数 |
| | `relationExpansion` | 布尔 | true/false | true | 是否启用关系图扩展 |

> 前端右侧参数面板按这些 schema **自动渲染**控件（枚举→下拉、整数→数字框、布尔→开关、数组→标签、对象→权重键值行）。加参数只改后端算子的 schema，前端零改动。

### 6.9 连接点速查（每个算子的输入/输出 slot）

类型简称：文本=STRING、向量=VECTOR、范围=SCOPE、查询理解=QUERY_UNDERSTANDING、候选=CANDIDATE_LIST、候选多入=CANDIDATE_LIST_MULTI、字符串列表=STRING_LIST、上下文包=CONTEXT_PACK。所有输入口均为必填。

| 算子 | 输入口 | 输出口 | 接法 / 限制 |
|---|---|---|---|
| `request_input` | （无） | `query`(文本) | 入口；query 接起点算子的 query 口。可不用（query 会自动绑定） |
| `query_embed` | `query`(文本) | `queryEmbedding`(向量) | query 可不连（自动绑定）；输出接 dense_vector |
| `hyde` | `query`(文本) | `queryEmbedding`(向量) | 同上，与 query_embed 可互换 |
| `query_understanding` | `query`(文本) | `understanding`(查询理解) | query 自动绑定；输出接 entity_exact / assemble |
| `multi_query` | `query`(文本) | `variants`(字符串列表) | ⚠️ 输出当前无下游算子可接 |
| `scope_resolve` | （无） | `scope`(范围) | 无输入；scope 一对多扇出到需要 scope 的算子 |
| `dense_vector` | `queryEmbedding`(向量), `scope`(范围) | `candidates`(候选) | queryEmbedding 接 query_embed/hyde；scope 必接 scope_resolve |
| `fts` | `query`(文本), `scope`(范围) | `candidates`(候选) | query 自动绑定；scope 必接 |
| `entity_exact` | `understanding`(查询理解), `scope`(范围) | `candidates`(候选) | understanding 接 query_understanding；scope 必接 |
| `graph_expand` | `seeds`(候选), `scope`(范围) | `candidates`(候选) | seeds 必接某检索器候选（不能独立起头）；scope 必接 |
| `rrf` | `candidates`(候选**多入**) | `candidates`(候选) | candidates 可接多条线 |
| `weighted_rrf` | `candidates`(候选**多入**) | `candidates`(候选) | 同上；权重按 source 名配 |
| `identity` | `candidates`(候选，单入) | `candidates`(候选) | 单路透传 |
| `model_rerank` | `candidates`(候选), `query`(文本) | `candidates`(候选) | candidates 接上游；query 自动绑定 |
| `llm_rerank` | `candidates`(候选), `query`(文本) | `candidates`(候选) | 同上 |
| `score_rerank` | `candidates`(候选) | `candidates`(候选) | 只需候选，不需查询 |
| `collect` | `candidates`(候选) | `candidates`(候选·**终点**) | 测试终点 |
| `assemble` | `candidates`(候选), `understanding`(查询理解), `scope`(范围) | `contextPack`(上下文包·**终点**) | 3 个输入都要连；生产终点 |

通用限制（所有算子）：① 右输出→左输入，类型须一致（唯一例外 候选→融合多入口）；② 普通输入口只接一条（再连替换），只有融合 candidates 多入；③ 无环、必须选一个终点；④ query 可不连（自动绑定），scope 必须连 scope_resolve；⑤ 类型不符连不上并提示。详见第 5 节「连线规则」。

## 8. 生命周期

```
[新建] → 草稿(可任意编辑/试运行)
   │
   ├─[校验]  编译检查（连线/类型/环/必填/参数）→ 不通过会列出具体节点/边
   │
   ├─[发布]  先校验通过 → 生成不可变版本 vN，状态变「已发布」
   │           └─ 版本内容不可变；可多次发布得到 v1/v2/v3…
   │
   ├─[回滚]  把「当前版本」指回某历史版本（版本本身不变）
   │
   ├─[归档]  状态→已归档（软隐藏，数据仍在，可在「已归档」页签看）
   │
   └─[删除]  仅对**已归档**的范式可删（两步防误删）；级联删除所有版本，不可恢复
```

- **草稿/已发布/已归档** 三个状态，列表按状态分页签。
- **发布版本号** = 历史最大版本 + 1（回滚后再发布也不会撞号）。

## 9. 运行：试运行 vs 运行已发布

右侧「运行」区：

- **试运行草稿（不落库）**：跑**当前画布**（含未保存改动），调 `POST /api/v1/paradigm/run`。用于编辑时快速看效果。
- **运行已发布**：选版本号（当前版本 / v1 / v2…），跑那个**不可变版本**，调 `POST /api/v1/paradigm/{id}/search?version=N`。这就是测试系统的调用方式。

结果面板展示：候选列表（id/source/score/text）或 ContextPack，以及每个算子的执行链路耗时。

## 10. 测试系统调用（接口）

范式发布后，编辑器右侧「接口调用」区可看到端点，并能**一键复制 curl**。

**调用已发布版本：**
```
POST /api/v1/paradigm/{paradigmId}/search?version={N}
Content-Type: application/json

{ "query": "aa-interface", "domain": "cloud_core_network", "channel": "prod", "debug": false }
```
- `version` 省略 = 用当前发布版本（latest）；指定 = 锁定该不可变版本（结果可复现）。
- `domain` 省略 = 默认领域；`channel` 省略 = 领域默认渠道。

**响应（取决于终点算子）：**
- 终点是 `collect` → `{ "candidates": [ { "id", "score", "source", "scoreChain", "metadata" }, ... ] }`
- 终点是 `assemble` → `{ "contextPack": { ...与 /api/v1/search 同结构... } }`
- `debug:true` 时附 `trace`（各算子耗时）。

**完整 curl 示例**（经 main_control 反代，与前端同源可直接跑；测试系统若直连 serving 把域名换成 serving 的 host:8081，路径不变）：
```bash
curl -X POST 'http://<host>/api/control-plane/api/v1/proxy/cloud_core_network/serving/api/v1/paradigm/pd-xxxxxxxx/search?version=1' \
  -H 'Content-Type: application/json' \
  -d '{"query":"aa-interface","domain":"cloud_core_network"}'
```

## 12. 常见问题 / 排错

- **画布没"模板"/没新功能** → 浏览器硬刷新（Ctrl+Shift+R）。
- **连线连不上** → 类型不符（看弹出的中文提示）；确认是右输出口→左输入口。
- **校验报 `missing_required_input`** → 某必填输入没连；检索算子的 `scope` 必须连 `scope_resolve`。
- **运行/发布报参数错误** → 数字框别留空（清空会回落默认值）；权重 key 别留空。
- **运行没结果但无报错** → 查询词不在语料里（换 `aa-interface`/`custom-record`/`application assurance`）；或 dense_vector 选了某 textKind 而该类无数据。
- **运行转圈较久** → 首次向量化要调嵌入服务（约 2 秒正常）。
- **删除按钮没有** → 只有「已归档」的范式才有删除（先归档）。
- **回滚后想再发布** → 直接发布即可，版本号自动取最大+1，不会撞号。
