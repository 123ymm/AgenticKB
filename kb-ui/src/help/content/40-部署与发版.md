# 40 · 部署与发版

本章整合自 `docs/部署指南-2026-09-01.md` 与 `docs/deployment/release-versioning.md`（旧文件暂保留原位，全书验收后统一退役，见 00-目录）。面向外网开发机（Windows）→ 内网服务器（Linux）。

**两句话总览**：

- **日常改动**（Python / 前端 / Java 代码）→ 增量同步包，约 15 秒应用，不重建容器；
- **基础设施改动**（依赖 / Dockerfile / nginx / supervisor / 全新服务器）→ 全量镜像。

**平台访问地址**：`http://<服务器IP>:8080`（`CMKB_UI_PORT` 默认 8080；部署脚本**禁止**宿主机 80，遇 80 占用按提示设环境变量换端口）。

## 0. 先判断走哪条路

```text
这次改了什么？
├─ 只是代码（.py / .vue / .ts / .java）──────────────→ 【A. 增量同步】
├─ pyproject.toml / pom.xml / package.json（加依赖）
├─ Dockerfile / docker-compose.yml / nginx.conf / supervisord.conf
├─ 或换全新服务器
│   ├─ 服务器还没部署过 ──────────────────────────→ 【B. 全量镜像-首次部署】
│   └─ 服务器已有旧版本 ──────────────────────────→ 【C. 全量镜像-升级】
└─ 只改内网配置（database.yaml / llm_service.yaml 等）→ 【D. 只重应用配置】
```

## A. 增量同步（日常，约 15 秒）

### A1. 外网开发机打包

```bash
# 改了 Java 先构建（没改跳过）：cd agent_serving_java && mvn -DskipTests package
# 改了前端先构建（没改跳过）：cd kb-ui && npm run build
bash deploy-sync.sh pack            # jar/dist 都带上
bash deploy-sync.sh pack --code-only  # 只改 Python，包更小
```

产出 `sync-<时间戳>.tar.gz`（约 15–35MB）+ `.sha256` 两个文件。

pack 自动做的事：

- **版本决策提醒**：显示 `releases.json` 当前版本，确认后继续（版本号在 releases.json 里改好再 pack，不在脚本里输）；
- 排除 `main_control_service/config/`（**内网配置永不被覆盖**）、剔除 `__pycache__`；
- 与上次成功 pack 基线（`.cmkb-sync-last/`）对比三个依赖清单——**有依赖变更会提醒改走全量镜像**。

### A2. 传输

两个文件一起传到内网服务器**仓库根目录**（隔离网用你惯用的摆渡方式；脚本注意 CRLF，见第 42 章）。

### A3. 内网应用

```bash
bash deploy-sync.sh apply sync-<时间戳>.tar.gz
```

脚本自动：sha256 校验 → 解包 → 安全复查（包内带 config/.env 直接拒绝）→ 逐目录**同 inode 内容同步**（清子项+拷入，**不 rename 目录**——bind-mount 锁 inode）→ config/场景包/domain_registry 原样保留 → **数据库迁移门禁（见下）** → 只重启内容有变化的服务（依赖序 control → llm → mining → serving → mcp；control 变更级联全部）→ 健康检查。

**⚠ 数据库迁移门禁（apply 内置，必读）**：apply 在重启新代码前执行 `database_upgrade plan → apply → verify` 三步：

- 迁移需要**停服**（按反向序 mcp → serving → mining → llm 停止）再切库——**期间服务短暂不可用是预期行为**；
- 轮换目标库已存在时，脚本要求**交互输入 `DELETE`** 确认才继续；**CI/无 TTY 环境安全失败**（不会自动删库），改由人工执行带 `--replace-target` 的 migration apply；
- 迁移失败**自动回滚**代码与配置并重启旧服务；回滚也未完成则服务保持停止并明示需人工介入。

| 改动 | 重启 | 耗时 |
|---|---|---|
| 只改前端 | 无 | Ctrl+F5 即见 |
| 只改某 Python 服务 | 该服务 | ~10 秒 |
| 改了 Java | serving | ~25 秒（Spring Boot 启动稍慢） |
| 改 main_control 代码 | control + 全部级联 | — |
| 含数据库迁移 | 先停服迁移再按序重启 | 视库大小 |

验证（仓库根执行）：

```bash
docker exec cmkb supervisorctl status        # 6 个服务应全 RUNNING
curl -fsS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/   # 应 200
```

### A4. 出问题时

| 现象 | 处置 |
|---|---|
| 校验失败 | 重新传输（两个文件必须一起） |
| 某服务重启后不健康 | 脚本停在明确提示；查 `./logs/<服务>.log`，修好后 `docker exec cmkb supervisorctl restart <服务>` |
| 同步了错误内容 | 重新 pack + apply 正确内容即可（apply 幂等） |
| **想回滚到上一版** | **服务器上重放上一个时间戳的 sync 包**（apply 幂等，旧包重放即回滚）——所以**服务器侧保留历史 sync-*.tar.gz** 作为回滚材料，不要随手清 |
| 想回镜像内置版本 | 走 C 路线 `--force` |

## B. 全量镜像 — 首次部署

1. **外网构建**：`bash deploy-build.sh` → `cmkb-<版本>.tar.gz` + `.sha256`（版本号=releases.json 的 `current`）；
2. **传输**：镜像归档 + `docker-compose.yml` + `deploy-server.sh` + `deploy-sync.sh` → 内网空目录（将成仓库根，如 `/opt/cmkb`）；
3. 前置：服务器有 docker / compose v2（离线安装包自备）；PG 从容器网络可达（pg_hba 放行 `172.30.30.0/24` 或配置子网）；
4. **内网执行**：`bash deploy-server.sh`——自动加载镜像 → 补齐宿主机代码目录 → 校验配置（缺失从镜像模板补齐）→ **auth.yaml 密钥首次自动生成**（随机）→ 容器重建 → 依赖序启动 6 服务 → 全量健康检查。

**部署后必做**（外网包里的配置只是模板）：

```bash
vi main_control_service/config/system/database.yaml      # 内网 PG 连接（host/port/dbname/user/password）
vi main_control_service/config/system/llm_service.yaml   # 内网 LLM 端点/密钥
vi main_control_service/config/domain_registry.yaml      # 内网领域库路由
bash deploy-server.sh --apply-config
```

首次管理员密码：看 `main_control_service/config/system/auth.yaml` 的 `bootstrap.admin_password`（首次部署随机生成；`deploy-server.sh` 输出里也有提示）。

首次部署同时会在仓库根生成 `.env`（600 权限）——**内部密钥文件**（serving/mcp 鉴权），**不要删除、不要外传**。

## C. 全量镜像 — 升级已有服务器（低频）

与 B 相同，两处不同：先删旧归档（避免 find 挑错版本——**但保留上一个版本的归档在别处，作为回滚材料**）；想让代码目录也更新时加 `--force`。

| 选项 | 实际行为（按脚本实测） |
|---|---|
| 无参 | 加载新镜像、重建容器；宿主机代码目录不动 |
| `--force` | 代码目录也换成镜像版本，**但保留宿主机全部配置**（脚本先把 `main_control_service/config` 复制进暂存快照再换入，auth.yaml/database.yaml 等都不丢） |
| `--force-config` | 用镜像模板**覆盖配置**：auth.yaml、database.yaml、domain_registry.yaml 全部回模板——**后果是全员登录失效、连不上 PG、域路由丢失**。仅配置结构升级时用；用前先备份：`cp -a main_control_service/config config.bak.$(date +%F)` |

**回滚路径**：全量升级出问题时——重新加载上一版归档（`docker load < cmkb-<旧版>.tar.gz`）→ 再跑 `deploy-server.sh`。所以旧归档删之前先挪走一份。

## D. 只改内网配置

服务器上直接改 yaml → `bash deploy-server.sh --apply-config`（重建容器）；轻量方式 `docker exec cmkb supervisorctl restart control`（下游会重新拉取）。

## 发版：版本号怎么定

唯一真相源是仓库根 `releases.json`：

1. `releases` 数组顶部加发布记录（版本、日期、标题、变更列表）；
2. `current` 改成该版本号；
3. 提交后 `bash deploy-build.sh`——构建用 `current` 生成镜像/离线包名（如 `coremasterkb-app:1.1.11`），与显式传入的 `CMKB_VERSION` 不一致会停止。

版本号约定：修复 `1.0.1`、兼容新功能 `1.1.0`、不兼容升级 `2.0.0`。

部署后所有用户可在左侧导航底部点版本号查看发布内容；apply 后 control 重启，前端"新版本"弹窗与 `/health` 即上报包里的版本。

## 不变式（脚本已强制，但请知悉）

1. 同步/部署**永不覆盖内网配置**（`main_control_service/config/` 全量保留）；
2. 同步包**永不携带 .env**；服务器本地 `.env` 只存 2 个自动生成的密钥（serving/mcp 内部鉴权），不从外网传、也不要删；
3. 镜像内产物双份（`/app/...` 运行路径 + `/image-seed/...` 种子自举，防空挂载 403）；
4. **依赖变更必须走全量镜像**（增量包不含依赖安装；pyproject 是 Python 依赖唯一真相源）。
