# 33 · 开发流程

本章整合自 `docs/开发与发布流程.md`（旧文件暂保留原位，全书验收后统一退役，见 00-目录）。

## 0. 前置认知（项目特性，必读）

- **配置唯一来源是 `main_control_service`**：mining / serving / llm 的应用配置都从主控拉，**服务不从 `.env` 读应用配置**。`main_control_service` 必须最先启动。
  - 注意区分：内网服务器仓库根的 `.env` 是首次部署自动生成的**内部密钥文件**（serving/mcp 鉴权密钥），必须保留；某些工具脚本（inspect_db/export_db）也读它拿连接参数。
- **代码改完必须重启对应服务才生效**（无热重载）：
  - Python（mining / llm / main_control / mcp）：`supervisorctl restart <name>`；
  - Java（serving）：必须**重新 build 镜像**（无 volume 挂载）；
  - 前端（kb-ui）：`npm run dev` 有 HMR；构建产物部署需重新 `npm run build`。
- **数据库是远程共享 PG**。测试只能打 `*_test` 库，**绝不**对生产库跑测试或清表。

### 环境准备（新人第一课）

| 依赖 | 要求 | 说明 |
|---|---|---|
| Python | anaconda 发行版（3.11+） | Windows 下 PATH 要带 `Library/bin`（libpq）；依赖清单以根 `pyproject.toml` 为唯一真相源 |
| Node | v24（v18 跑不动 Vite） | kb-ui 构建用 |
| JDK + Maven | 按 `agent_serving_java/pom.xml` | `mvn -o test` 离线优先 |
| PG 连接参数 | 以 `main_control_service/config/system/database.yaml` 为准（host/user/password） | 测试库名必须 `_test` 结尾 |

### 本地起整套服务的两条路线

| 路线 | 适用 | 入口 |
|---|---|---|
| Docker Compose 一把起 | 最快见效 | `docker compose build app && docker compose up -d`（细节与坑见第 41 章本机调试） |
| 裸机按序起 | 调 Python 服务 | `python -m main_control_service` → `python -m llm_service` → `python -m knowledge_mining.mining.api` → `python -m mcp_server`（serving/前端另需 jar 构建与 npm build） |

> 前端 `npm run dev` 隐性依赖：`vite.config.ts` 只代理 `/api/control-plane → localhost:8910`，其余 API 全走 proxyClient 经主控转发——**dev 前必须先起 main_control 且 domain_registry 可用**，否则页面请求全挂。

## 1. 分支与提交

1. 从最新 master 切分支（不在 master 上直接提交）：

   ```bash
   git checkout master && git pull origin master
   git checkout -b <type>/<short-desc>     # 如 fix/kb-mining-bugs2、feat/xxx
   ```
2. 按工作面分批提交，每批一个 coherent commit，写清根因+修法：
   - 类型：`feat / fix / refactor / docs / test / chore / perf / ci`；
   - 一条 commit 只做一件事；跨前后端的大改动拆"后端一批 + 前端一批"；
   - message 正文写根因（最好附联调实测数据）+ 修法。
3. 提交前自检：`git status` 只含预期文件；IDE 噪声（如 `kb-ui/components.d.ts`）`git restore` 清掉。

## 2. 本地验证（提交前必跑）

### 后端（knowledge_mining）

```bash
# Windows：anaconda python，PATH 要带 Library/bin（libpq）
export PATH="/c/ProgramData/anaconda3/Library/bin:$PATH"
PY="/c/ProgramData/anaconda3/python.exe"

"$PY" -m py_compile <改动的.py>        # 语法快检（秒级）

# 相关测试（必须 _test 库 + 清表护栏；连接参数见 database.yaml）
PG_HOST=… PG_PORT=5432 PG_DBNAME=<库名_test> \
PG_USER=… PG_PASSWORD=… KB_ALLOW_TEST_TRUNCATE=1 \
  "$PY" -m pytest knowledge_mining/tests/kb/ -q
```

> 库名必须 `_test` 结尾（conftest 护栏）；远程库往返 ~40–80ms，kb 全量 ~3.5min，可 `-k <名>` 过滤。

### 前端（kb-ui）

```bash
npm run build --prefix kb-ui        # vue-tsc 类型检查 + vite 构建，全绿才能合
cd kb-ui && npx vitest run --reporter=dot   # 单测（可选）
```

> Node 用 v24。**不要用 `vue-tsc --noEmit` 代替 build**——references-only 根 tsconfig 下是空检查假通过（铁律见 superpowers 计划 / 53 号）。

### Java（agent_serving_java）

```bash
cd agent_serving_java
rm -rf target/classes target/test-classes && mvn -o test    # 强制全量重编（增量编译会假绿）
```

## 3. 推送与 PR

1. `git push -u origin <branch>`；
2. GitHub 建 PR：`base: master ← compare: <branch>`；冲突回本地 `git rebase origin/master`；正文写清做了什么/根因/验证证据/部署注意；
3. 合并方式选 **Create a merge commit**，**不要 Squash**（会丢批次历史）；
4. 合并后先别删分支，等本地同步完再删。

> CI：`.github/workflows/build.yml` 在 push master 时构建镜像并推 GHCR——PR 合并后可去 Actions 看构建结果；镜像构建约 3 分半，fork 场景注意 GITHUB_TOKEN 的 packages:write 权限。

## 4. 合并后本地同步 + 清理

```bash
git checkout master && git pull origin master
git branch -d <branch> && git push origin --delete <branch>
```

> 坑：切分支前若有幻影改动（`git diff` 为空但 status 显示 modified，多为 CRLF），`git restore` 清掉。

## 5. 部署上线（按序）

让线上生效的完整路径见第 40 章（增量同步 15 秒）。本地调试顺序：

```bash
python -m main_control_service          # 1. 必须最先（配置中心）
python -m llm_service                   # 2.
python -m knowledge_mining.mining.api   # 3. 改了 mining 必重启
python -m mcp_server                    # 4. MCP 服务
cd kb-ui && npm run build               # 5. 前端构建产物
# serving 改了 application.yml / Java → 必须重新 build 镜像后重启
```

### 品牌外观（网站名/图标）

站名、favicon、侧栏 logo 运行时可配：`main_control_service/config/system/ui.yaml` 的 `site:` 块。系统设置 → 品牌外观 Tab 表单保存即生效；改名/换标**无需**重建前端镜像（值在 volume 挂载的 ui.yaml）。整站一份，不按域区分。

### 用户权限首上线（一次性，运维动作）

1. 迁移 `databases/kb/schemas/006_kb_users_auth.sql`（`pg_schema.py`/`reset_db.py` 自动跑）；
2. 放 `config/system/auth.yaml`，把 `jwt_secret` / `internal_verify_secret` / `bootstrap.admin_password` 改为强随机值；
3. 重启 main_control（读 auth.yaml + 装鉴权中间件）→ 重启 mining（播种首 admin：用户名 `admin` + bootstrap 密码）→ 重建 kb-ui 镜像；
4. `admin` 首登立即改密 → 用户管理建普通用户。

日常加/改用户纯运行时操作，无需重启。锁死恢复：auth.yaml `enabled: false` 再重启 main_control（fail-closed）。

> 首次部署通常由 `deploy-server.sh` 自动生成 auth.yaml 密钥（第 40 章 B 路线），本节适用于手工环境。

## 6. 挖掘相关运维要点

改了挖掘算子/范式/域包策略后，已挖文档**不会自动重生**（哈希去重 → SKIP 复用旧快照）。应用新逻辑：重启 mining → 强制重挖（勾选/整库/文件多选）。范式签名变更（版本/图变）自动 force_redo，无需人工勾。

常见坑见第 42 章汇编。

## 7. 速查：一次完整迭代

```text
master 最新 → 切分支 → 改代码 → py_compile/pytest/build 验证 →
分批 commit → push -u → GitHub PR（merge commit，不 squash）→
合并 → checkout master + pull + 删分支 → 增量同步部署（第 40 章）→ 强制重挖验证
```
