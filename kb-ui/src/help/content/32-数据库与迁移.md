# 32 · 数据库与迁移

## 总貌

- PostgreSQL 是**业务事实源**（目录、权限、Document 当前态、快照、对象引用清单），MinIO 只存字节（ADR D2）；
- 远程共享 PG；**库名以 `main_control_service/config/system/database.yaml` 为准**（开发文档示例 `kb_db`，实际部署各有配置）；
- **测试只能打 `*_test` 库**（conftest 护栏：库名必须以 `_test` 结尾 + `KB_ALLOW_TEST_TRUNCATE=1` 才允许清表）；
- SQL 模板在 `databases/` 下分目录维护：`kb/schemas`（编号迁移，如 `006_kb_users_auth.sql`、`014_mcp_keys.sql`）、`migrations`、`bootstrap`、`mining_control`、`mining_runtime`、`agent_llm_runtime`、`asset_core`、`ontology`；
- 运行库结构由各服务 `pg_schema.py` 启动时自动应用。

## offline_rebase：两个库来回换（52-18 号）

数据库结构大改（如退役 21 张表）用 `offline_rebase` 完成：

- 目标库**固定轮换**：`x → x_converged`，下一次 `x_converged → x`——**只有两个库来回换，不再生成时间戳目标库**；
- 目标已存在时默认拒绝；只有操作者明确确认或 CLI 显式 `--replace-target` 才能删除重建；
- 迁移有三模式与**003 校验门禁**，部署前先预检预演（migration manifest 见 `databases/migrations/`）。

## 数据字典

`docs/数据字典/AgenticKB-数据字典.html` 由 `build_dictionary.mjs` 生成——**但数据源是 `docs/数据字典/_work/` 下三个手工维护的 JSON 批次**（batch_asset / batch_v2_ontology / batch_runtime），**不直接解析 `databases/` 的 SQL**。表结构变更后：先更新 `_work/*.json`，再跑脚本重建 HTML。

## 核心数据不变量（写代码必读）

- **知识产物只跟快照走**：快照回收则产物全删；快照按内容指纹域级共享，同内容跨库同一行（50 号）；
- 快照废弃轨道：`lifecycle_status='DEPRECATED'` 留 7 天 → 独占才回收；指纹命中可复活（DEPRECATED → READY）；
- 当前可搜索集合 = 每文档最新 validated/published Build 的 active 选择，过滤软删——**serving 侧 CTE 三处（检索/统计/质量）口径必须同步修改**；
- 域是拥有者、库成员和 public 可见性的共同外层边界（除站点管理员）；站点管理员角色在 `kb_users`，域管理员/成员在 `user_domains`——三种角色是跨两字段的逻辑模型；
- MCP：单用户、单域、多钥匙（部分唯一索引约束）。

## 给开发者的操作提醒

| 场景 | 做法 |
|---|---|
| 本地跑测试 | `PG_DBNAME=<*_test 库> KB_ALLOW_TEST_TRUNCATE=1`，连接参数以 `database.yaml` 为准（远程库往返 40–80ms/查询，kb 全量约 3.5 分钟，可 `-k` 过滤） |
| 加表/改表 | SQL 模板进 `databases/` 对应目录，带编号；先在 `_test` 库验证 |
| 存量库删表 | 走 52-18 号的 offline_rebase 流程，先预检预演；增量部署时 apply 内置迁移门禁（见第 40 章） |
| 看库 | `inspect_kb_state.py`（要 PG 环境变量）；注意 `inspect_db.py`/`export_db.py` 读仓库根 `.env` 的连接变量（与"应用不读 .env"不冲突——那是服务运行时规则），用法见第 41 章 |
| 全量导出/导入 | `export_db.py` / `import_db.py` |
